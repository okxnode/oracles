# 安全与开源注意事项

**这份文档是 push 前的必读清单。** 这个项目开源出去以后，
一个不小心泄露的凭据就足以让人接管你所有的云主机。

---

## 一、push 之前的检查清单

逐条打勾：

```bash
# 1. 扫一遍工作区
./scripts/check_secrets.sh

# 2. 确认敏感文件没被跟踪
git ls-files | grep -E 'accounts\.json|\.pem$|\.key$|^\.env$|oracles\.env'

# 3. 看一眼暂存区到底改了什么
git diff --cached
```

- [ ] `scripts/check_secrets.sh` 输出 `✅ 扫描通过`
- [ ] 第 2 条命令**没有任何输出**
- [ ] `git diff --cached` 里没有真实 OCID、没有私钥、没有 Bot Token
- [ ] `accounts.json` 里还是 `accounts.example.json` 那份占位内容（或者根本没这个文件）
- [ ] `.env` / `oracles.env` 没被跟踪
- [ ] 文档和截图里没有真实 IP、OCID、账号别名

### 装成 pre-commit 钩子

```bash
ln -sf ../../scripts/check_secrets.sh .git/hooks/pre-commit
chmod +x scripts/check_secrets.sh
```

之后每次 `git commit` 都会自动扫一遍，有问题直接拦下。

### CI 侧兜底

`.github/workflows/secret-scan.yml` 在每次 push/PR 时：

1. 跑 `check_secrets.sh --verify` —— 先证明**规则本身**能命中目标样本
2. 跑 `check_secrets.sh` 精确扫 OCI / Telegram 凭据特征 ← **主闸门**
3. 跑 `gitleaks` 扫完整 git 历史（不只看最新提交）← **补充网**
4. 跑单元测试（Python 3.10 / 3.12）

**本地钩子可以不装，CI 一定会跑。**

#### ⚠️ 顺序不能调：主闸门必须在 gitleaks 之前

GitHub Actions 一旦某步失败就**中止后续步骤**。如果把 gitleaks 排前面，
它报一个假阳性就会让真正的主闸门**根本不运行**。

实测注入 7 类本项目的真实密钥：

| 密钥类型 | `check_secrets.sh` | gitleaks |
| --- | :---: | :---: |
| Telegram Bot Token | ✅ | ❌ |
| OCI OCID（user / tenancy） | ✅ | ❌ |
| API 指纹 | ✅ | ❌ |
| PEM 私钥 | ✅ | ✅ |
| S3 AccessKey | ✅ | ❌ |
| 私钥文件路径 | ✅ | ❌ |
| 疑似 SecretKey | ✅ | ❌ |
| **合计** | **7/7** | **1/7** |

原因：gitleaks 的默认规则集是按「通用密钥形态」设计的，不认识 `ocid1.`
这种厂商特有前缀，也不认识 Telegram 的 `<数字>:<35位>` 形态。

> **不要把开源安全托付给第三方扫描器。** 它不认识你的威胁模型，
> 也不认识你的约定。它可以当补充网，但不能当主闸门。

#### `.gitleaks.toml` 是干什么的

gitleaks **不认识**本仓库的 `secret-scan:allow` 行内标记。而仓库里必然有
若干测试夹具要长得像真密钥（否则没法验证脱敏功能本身），于是它每次都报，
CI 每次都红 —— 而**一个红久了的检查等于没有检查**，大家会开始无脑忽略它。

所以仓库根目录有一份 `.gitleaks.toml`，把本仓库已经明确判定为虚构的东西
**精确翻译**成 gitleaks 能理解的语言。它只做两件事，**不放松任何规则**：

- 豁免带 `secret-scan:allow` 标记的**那一行**（与本地脚本同一个约定）
- 整份跳过两个「自己扫自己必然全红」的文件（与 `SKIP_FILES` 保持一致）

⚠️ **尤其不能**加 `EXAMPLE` / `example` 这类通用 allowlist ——
真实凭据完全可能带这些字样，放行就等于给泄露开口子。

⚠️ 改完 `.gitleaks.toml` 必须验证它没变成橡皮图章：往任意源码文件里塞一个
**形态真实**的密钥，确认扫描照样会红。做法见
[踩坑清单](06-踩坑清单.md) 第 35 条。

### 豁免标记 `secret-scan:allow`

测试夹具和文档示例里**必须**出现 OCID / PEM 这类字符串 ——
否则没法验证脱敏功能本身。这类行加行内注释即可跳过扫描：

```python
out = short_ocid("ocid1.instance.oc1.some-region-1.abcdefghijklmnop")  # secret-scan:allow
```

⚠️ **标记必须和匹配内容在同一行**（扫描是按行过滤的）。

⚠️ 这个标记是**给人看的承诺**。加之前先问自己：这真是虚构的吗？
随手加标记比不加标记更危险，因为它会让你以为有防护。

### 占位符白名单

`check_secrets.sh` 里有一个 `PLACEHOLDER` 列表，放的是「人一眼就知道是假的」模式：

```
EXAMPLE / Example / REPLACE / replace / your- / xxxx
deadbeef / DEADBEEF
00:11:22:33:44:55:66:77:88:99:aa:bb:cc:dd:ee:ff   （顺序递增的指纹）
aa:bb:cc:dd:ee:ff:00:11:22:33:44:55:66:77:88:99
你的 / 在此 / 示例 / 占位
```

⚠️ **列表里没有、也永远不能有 `aaaa`。**
真实 OCID 的随机段几乎都以 `aaaa` 开头，加进去就等于把 OCID 检查整条废掉。
示例文件里的 OCID 靠 `EXAMPLE` 就能过滤掉。

（本文档曾经把 `aaaa` 错列在上面 —— 而 `check_secrets.sh` 里恰好写着
「不要加 `aaaa` 进来」。**文档和代码说法相反时，代码是对的，但文档会把
下一个人带进坑里**，所以看到就改。）

**往这个列表里加东西要非常克制** —— 每加一条就是给泄露多开一个口子。

> 本项目开发过程中，扫描器真的抓到过一次：写测试夹具时从真实配置里
> 抄了 `fingerprint` 和 S3 Access Key 前缀。这正是它存在的意义 ——
> **人是会不小心的，所以要有机器盯着。**

## 二、已经做了什么

### 密钥隔离（架构级）

```
仓库（push 到 GitHub）           配置目录（永不进仓库）
─────────────────────────       ──────────────────────────
accounts.example.json     ──▶   $ORACLES_HOME/accounts.json   (600)
.env.example              ──▶   $ORACLES_HOME/oracles.env     (600)
                                $ORACLES_HOME/keys/*.pem       (600)
                                $ORACLES_HOME/keys/<账号>/     (700)
                                  ├─ login_key                 (600)
                                  └─ login_key.pub             (644)
```

配置目录默认 `~/.oracles`，生产用 `/etc/oracles` —— **在仓库目录之外**。
这不是靠 `.gitignore` 拦，而是密钥根本不在工作区里。

> ⚠️ 最后那两行（`login_key`）**不是**「本来就在外面」这么简单：
> 它是 Bot 现场生成的**账号级登录密钥对**，私钥会**真的落在服务器上**。
> `.gitignore` 里额外加了 `keys/` / `login_key` / `login_key.pub` 三条 ——
> 因为上面那条 `*.key` **兜不住它**：私钥文件名没有扩展名。
> 一旦有人把 `ORACLES_HOME` 指到仓库内，靠的就是这三条。

#### 🔑 登录密钥：一个必须说清楚的安全权衡

开机向导的「SSH 公钥」下有两条路：

| 选项 | 私钥在哪 | 说明 |
| --- | --- | --- |
| **用我配置的公钥**（默认） | **只在你自己机器上** | 注入你的 `~/.ssh/*.pub`，私钥从不外流 |
| 让 Bot 生成一对新的 | **服务器上 + 经过 Telegram** | 生成后存 `<ORACLES_HOME>/keys/`，并发文件给你 |

选第二条会带来两个**真实**的暴露面：

1. **私钥落在 VPS 上** —— 谁拿到那台机器（或它的备份、快照），
   就拿到该账号下**所有**实例的钥匙。
2. **私钥经过 Telegram 服务器** —— 和救援控制台的私钥一样（项目里已有先例）。

所以它**不是默认路径**：必须用户在向导里主动点「🆕 让 Bot 生成一对新的」。
默认仍然是「用我配置的公钥」。

> **OCI 侧没有别的选择。** 实测（SDK 2.186.0）：`ComputeClient` 里名字含
> `key` 的方法 **0 个**，`LaunchInstanceDetails` 只收 `metadata`
> （`ssh_authorized_keys` 塞在这个 dict 里）。控制台里那个
> 「Generate a key pair for me」是**浏览器本地生成**的，不是服务端下发的 ——
> 要复刻这个体验，只能自己在服务器上生成。

**用哪把钥匙登录哪台机器，可以当场核对**：实例菜单的「🔑 下载登录密钥」
会先读实例 metadata 里的 `ssh_authorized_keys`，和本账号存的公钥比指纹。
不一致就明说「这把钥匙开不了这台机器」，并列出实例上**实际**注入的指纹 ——
而不是给一句「可能不适用」的免责声明。

### .gitignore

覆盖：`*.pem` `*.key` `si*.pem` `accounts.json` `.env` `bot.env`
`backups/` `logs/` `*credentials*.txt` `s3-*.txt`，以及常规的语言产物。

注意 `!accounts.example.json` 和 `!.env.example` —— 示例文件要保留。

### 脱敏（`oracles/redact.py`）

在日志离开进程之前、在消息发到 Telegram 之前，把这些替换成占位符：

| 模式 | 例子 |
| --- | --- |
| OCID | `ocid1.tenancy.oc1..aaaa…` → `<OCID 已隐藏>` |
| PEM 私钥 | 整块 → `<PEM 私钥已隐藏>` |
| API 指纹 | `a8:36:29:…` → `<指纹已隐藏>` |
| Telegram Token | `1234567890:AAH…` → `<Telegram Token 已隐藏>` |
| S3 Access Key | 40 位十六进制 → `<S3 Access Key 已隐藏>` |
| base64 密钥 | 44 字符 → `<密钥已隐藏>` |

**为什么需要这个**：OCI 的报错信息里经常夹带 OCID；
`oci` SDK 的 DEBUG 日志会打印整个请求体，里面可能有 `user_data`。
这些内容一旦进了日志、又被贴到 issue 里，就等于公开。

脱敏挂在 **logging handler** 上而不是 logger 上，所以第三方库
（`oci`、`httpx`、`telegram`）打的日志同样会被过滤。

审计报告里展示的「疑似明文密码」片段也会先打码 ——
否则审计报告本身就成了密码泄露渠道。

### 日志降噪

```python
logging.getLogger("oci").setLevel(logging.WARNING)
```

OCI SDK 的 DEBUG 日志会把整个请求体打出来。即使有脱敏过滤，
也没必要让它产生这些内容。

### 白名单默认拒绝

```python
if not settings.allowed_user_ids or uid not in settings.allowed_user_ids:
    return  # 静默拒绝
```

`TELEGRAM_ALLOWED_USER_IDS` 留空时**谁都不放行**，而不是「没配就放开」。
一个能删你云主机的 Bot 裸奔在网上，被人搜到就是灾难。

未授权访问会记日志：`拒绝未授权访问 user_id=... username=...`，
并把你的 ID 回给对方（方便你把它加进白名单）。

## 三、写操作的防护层次

```
第 1 层  Telegram 白名单          —— 只有你能发指令
第 2 层  ORACLES_WRITE_ENABLED    —— 关掉时所有写操作变 DRY-RUN
第 3 层  ORACLES_ALLOW_DESTRUCTIVE—— 销毁/删除类单独再拦一层
第 4 层  两段式计划确认            —— plan_* 只读，execute_* 才写
第 5 层  执行前实时复核            —— 不信任计划里的快照
第 6 层  池成员/多义匹配拦截       —— 该拦的直接拦
```

### 第 4 层：结构上的 DRY-RUN

```python
plan = plan_launch(client)        # 只读：挑 AD、查配额、找镜像、验块存储
show(plan.render())               # 给人看
# ...用户点「确认执行」...
execute_launch(client, plan)      # 才真正调 API
```

DRY-RUN **不是**「在写操作里加个 `if`」，而是分成两个函数 ——
调用方必须先拿到计划、展示给人看、人确认之后才调 execute。
结构上就不存在「不小心直接执行」的路径。

### 第 5 层：执行前实时复核

这些地方刻意**不信任**计划里的快照：

| 操作 | 复核内容 |
| --- | --- |
| 创建实例 | 重新查一次目标 AD 的余量（等确认期间可能被别人用掉） |
| 销毁实例 | 重新查实例状态 + 重新做池成员检查 |
| 删除桶 | 重新列一次对象清单（不信任扫描快照） |
| 删除块卷 | 重新拉一次挂载关系。**已挂载的拒绝；挂载关系没查到的也拒绝** —— 判据是「确认它没挂」，不是「没查到它挂着」 |
| 删除孤儿卷 | 同上，且复核结论把「已挂载」和「没查到」**分开报**（原因不同，不能合成一句） |
| 收紧安全列表 | 重新 get 一次规则再改 |

### 第 6 层：主动拦截

- **实例池成员不能直接销毁** —— 删了池会在几十秒内再补一台，等于白删
- **名称多义匹配报错** —— `'e2-ubuntu'` 匹配到 3 台时拒绝执行，让你补全
- **`allowed_cidr` 不能是全网** —— 填 `0.0.0.0/0` 等于没加固，直接拒绝
- **空桶判定必须确定** —— 拿不到明确的空列表就抛错，绝不猜
- **删卷前的挂载复核必须确定** —— 挂载关系没查全就拒绝。
  这里曾经是反的：`availability_domains()` 失败会 fail-closed（一台都不删），
  而**逐 AD** 的挂载查询失败却 fail-open（当成没挂 → 照删）。
  同一个函数里两种失败语义并存，只看代码很难觉得有问题（见踩坑 #63）

### 写操作唯一出口

所有写操作都经过 `oracles/bot/dispatch.py`。写开关的判定**只在这一处**，
不散落在各个 handler 里 —— 散落的判断早晚会有漏网之鱼。

CLI **完全没有写操作**：命令行没有确认环节，一按回车就执行，太容易出事。

## 四、如果你已经泄露了

**光删文件没用。** git 历史里的内容仍然可以被 `git log -p` 翻出来，
GitHub 的 fork 和缓存也可能留着。必须**吊销凭据**：

### 1. 立即吊销 OCI API 密钥

OCI 控制台 → 我的概要文件 → API 密钥 → 删掉泄露的那个。

删掉后那份私钥立刻失效，即使别人手里有也没用。

### 2. 吊销 Telegram Bot Token

BotFather → `/mybots` → 选 Bot → API Token → **Revoke current token**。
重新生成一个填回 `oracles.env`。

### 3. 吊销 S3 兼容密钥

OCI 控制台 → 我的概要文件 → Customer Secret Keys → 删掉。

### 4. 检查有没有被动手脚

```bash
# 用 CLI 查有没有多出来的资源
python -m oracles.cli instances
python -m oracles.cli buckets
python -m oracles.cli audit        # 计费残留
python -m oracles.cli security     # 安全组有没有被改
```

重点看：有没有不认识的实例、有没有被开的端口、有没有异常的出站流量。

### 5. 清理 git 历史（可选）

吊销凭据之后，历史里留着也无害了。如果实在想清：

```bash
# 需要 git-filter-repo
pip install git-filter-repo
git filter-repo --path accounts.json --invert-paths
git push --force
```

⚠️ 这会重写历史，所有协作者都要重新 clone。
**先吊销凭据，再考虑清历史** —— 顺序反了没有意义。

## 五、给别人用这个项目时

如果你的读者要用这个项目，提醒他们：

1. **不要**把你的 `accounts.json` 提交上去 —— 用 `accounts.example.json` 做模板
2. **不要**在 issue 里贴完整日志 —— 先确认脱敏有没有漏
3. **先跑只读模式** —— 点各种按钮看计划内容对不对，再开写权限
4. **`ORACLES_ALLOW_DESTRUCTIVE` 随用随开** —— 平时保持 false
5. **私钥权限 600** —— `ls -l` 确认一下

### 关于 issue / PR 里的信息

即使有脱敏，也建议：

- 贴日志前扫一眼有没有真实 IP（脱敏不覆盖 IP）
- 账号别名可能暴露你的用途，改成「账号 A」
- 报 bug 时用 `scripts/selftest.py` 的输出，它本来就是设计给人看的

## 六、这个项目不做什么

明确划出边界，避免误解：

- **不绕过 OCI 的任何限制** —— 只是把官方 API 包装成好用的界面
- **不存储你的凭据到任何第三方** —— 所有请求直连 OCI
- **不自动帮你「抢机器」** —— 没有后台轮询抢配额的功能
- **不代管账单** —— 审计功能只是调用官方 API 列出资源，
  具体费用以 OCI 账单为准
- **不做多用户** —— 这是一个人的工具，白名单里的都是你自己

## 七、依赖安全

```bash
# 检查依赖有没有已知漏洞
pip install pip-audit
pip-audit

# 或
pip list --outdated
```

主要依赖只有两个（`oci`、`python-telegram-bot`），攻击面很小。
`boto3` 是可选的，只有你想用 S3 兼容 API 时才需要装。

### 供应链

- `deploy/install.sh` 用 `pip install -e .` 从本地装，不从 PyPI 拉本项目
- systemd unit 用绝对路径的 venv Python，不依赖 PATH
- CI 里没有 `curl | bash` 之类的模式
