# 踩坑清单

64 个**实测踩过**的坑，按危险度排序 —— 前四条能让你丢数据或白花钱。

标注 🔬 的是用官方 SDK 时特有的（跟 CLI 时代的表现不一样）。

其中 **🧯 元坑**（26 条）不是 OCI 的坑，而是「让检查本身失效」的坑。
那一节建议至少读一遍 —— 业务坑出错你能看见，元坑出错你看不见。

---

## 🔴 一级：会造成数据丢失或持续计费

### 1. 免费配额绑在**单个可用域**上，不是整个区域

```
账号 13  us-ashburn-1   AD-1: 0 核   AD-2: 0 核   AD-3: 2 核
账号 17  eu-frankfurt-1 AD-1: 0 核   AD-2: 2 核   AD-3: 0 核
账号 9   us-ashburn-1   AD-1: 2 核（已用尽） AD-2: 0   AD-3: 0
```

**后果**：任何「取第一个 AD 就 launch」的实现，对账号 13/17 会**永远**挑到
0 配额的 AD-1，报错还会被误判成 `Out of host capacity`。

**两个推论**：

- 同一区域内不同账号的配额**互不相干**（账号 9 和 13 都在 us-ashburn-1，
  但配额完全独立）→ 不能按区域汇总
- 同一账号内不同 AD 的配额也**互不相干** → 不能取第一个

**正确做法**：

```python
cap = account_capacity(client)            # 逐 AD 查
ad  = pick_availability_domain(cap)       # 挑可开台数最多的
plan = plan_launch(client, ad=ad)
```

**容量公式**：

```
某 AD 可开台数 = min(该 AD 的 CPU 余量, floor(块存储余量 / 47))
账号可开总数   = Σ 各 AD 可开台数        ← 必须逐 AD 求和
```

### 2. `bootVolumeQuota` 报的是**块存储**满，不是 CPU 满

```
Service limit reached: bootVolumeQuota
```

看到这个别去查 CPU 配额。免费账号每租户只有 **200 GB 块存储**
（引导卷 + 数据卷共用同一池），池子满了就开不出实例，
**哪怕 E2.1.Micro 的 2 核配额还有剩**。

**常见元凶：孤儿引导卷。** 一块 150 GB 的残留卷就能吃掉 75% 额度。

**判定方法**：列引导卷 → 列挂载关系 → **确认**没挂在任何实例上的才是孤儿。

⚠️ 两个反直觉点（2026-09-21 实测，见 #62/#63）：
1. `ATTACHING`（正在挂载）和 `DETACHING`（还没真正脱离）**也算被占着**。
   只认 `ATTACHED` 会把**开机过程中**的引导卷判成孤儿。
2. **查询失败不等于「没挂」** —— 那是「不知道」。挂载关系没查到时必须
   按「可能挂着」处理，否则一次限流就能让清理功能删掉运行中实例的系统盘。

⚠️ 这个限额名 **不在 limits 列表里**（`limits definition list --service-name
block-storage` 只返回 8 个名字），它是内部 quota 家族名。别去 limits 里找。

**相关限额名**：

| 限额名 | 说明 |
| --- | --- |
| `total-free-storage-gb-regional` | 区域级，**查询无需 AD**（推荐，一次拿全） |
| `total-free-storage-gb` | AD 级，需 `--availability-domain` |
| `volume-count` | 卷数量上限，免费账号给到 10000，**几乎永远不是瓶颈** |

### 3. 🔬 `list_objects` 返回的是 `ListObjects` 模型，**不是 list**

```python
resp = client.object_storage.list_objects(namespace_name=ns, bucket_name=b)
# resp.data 的真实结构：
#   ListObjects(objects=[...], prefixes=[...], next_start_with=None)

for obj in resp.data:        # ✗ TypeError: 'ListObjects' object is not iterable
for obj in resp.data.objects:  # ✓
```

**这是本项目实际踩到的 bug** —— 表现是「桶的对象数显示为 `None`」，
因为异常被 `with_stats` 的 try/except 吃掉了。

CLI 时代没有这个问题（CLI 已经把 `.objects` 摊平成了 `data`），
所以从 CLI 迁移到 SDK 时特别容易中招。

### 4. 🔬 对象列表的分页游标在**响应体**里，不在响应头里

```python
# ✗ 通用分页器只看 opc-next-page 头，对 list_objects 无效
oci.pagination.list_call_get_all_results(client.object_storage.list_objects, ...)
# → 只返回第一页（默认 1000 个），超过 1000 个对象会被静默截断

# ✓ 手工循环，用响应体里的 next_start_with
start_with = None
while True:
    kwargs = {"namespace_name": ns, "bucket_name": b, "limit": 1000}
    if start_with:
        kwargs["start_with"] = start_with
    page = client.call(client.object_storage.list_objects, **kwargs)
    ...  # 处理 page.objects
    start_with = page.next_start_with
    if not start_with:
        break
```

**同一个坑的反面**：`list_object_versions` 走的是响应头 `opc-next-page`。
**两个接口的分页机制相反**，别想当然。

**后果**：一个超过 1000 个对象的桶，会被误判成「只有 1000 个」，
删桶时以为清空了其实没清空。

### 5. 「空桶」和「查询失败」必须是两个结果

**历史险情**：早期用 CLI 时，空桶的 JSON 返回体里**根本没有 `data` 键**
（形如 `{"prefixes": []}`），而失败时退出码非 0 但 stderr 可能为空。
当时用 `j.get("data", [])` 兜底，结果「查询失败」被静默成「0 个对象」，
于是「空桶」判定成立 → **差点删掉用户有数据的桶**。

**现在的实现**：

```python
raw = getattr(page, "objects", None)
if raw is None:
    raise OciApiError("...无法确认桶是否为空（不代表空桶）...")
```

`objects == []` 才算空桶；`objects is None` 一律抛错。
SDK 让失败会抛异常，但**显式检查**这个语义，把这个坑焊死。

**推论：绝不在查询结果上写 `or []` 兜底。**
`call()` 刻意不提供「失败返回空列表」的版本 —— 空列表和「查不出来」必须能区分。

### 6. 删桶被 `PreauthenticatedRequestStillExists` (409) 阻塞

即使桶已清空，只要桶上还挂着**预认证请求(PAR)记录**，删桶就会被拒：

```
code: PreauthenticatedRequestStillExists
message: Active Preauthenticated Requests still exist for bucket 'xxx'.
```

⚠️ **过期的 PAR 同样挡路。** OCI 只检查记录是否存在，不看是否过期。
实测有 2022 年就过期的 PAR 到 2026 年还在阻塞删桶。

**删桶完整顺序**：① 清空对象 → ② 删 PAR → ③ 删桶 → ④ 核验。

### 7. 删池内实例 = 白删

`terminate` 掉一个由实例池管理的实例后，池会在几十秒内**再开一台一模一样的**。

**要减机必须**：改池的 `size`，或先 detach。

```python
# 识别某台实例是否属于池
pools = client.call_all(client.compute_management.list_instance_pools, ...)
for pool in pools:
    members = client.call_all(
        client.compute_management.list_instance_pool_instances,
        compartment_id=..., instance_pool_id=pool.id)
    for m in members:
        instance_id = m.id      # ⚠️ 字段是 id，不是 instance_id
```

本项目的 `plan_terminate()` 会**主动拦截**池成员并拒绝执行。

### 8. 删实例时引导卷的默认行为：**SDK/CLI 和控制台相反**

| 途径 | 默认 |
| --- | --- |
| 控制台 | **保留**引导卷（复选框默认不勾）→ **孤儿卷的主要来源** |
| SDK / CLI | **删除**引导卷（`preserve_boot_volume` 默认 `False`） |

另一处不对称：`preserve_data_volumes_created_at_launch` 默认是 **`True`**（保留）。
即「引导卷默认删、数据卷默认留」。

**本项目显式传参**，不依赖默认值，并在计划里明确写出来
（「引导卷：一并删除」/「保留（会变成孤儿卷）」）。

## 🟠 二级：会导致功能失败或误判

### 9. 限额名是 `standard-e2-micro-core-count`

不是 `standard-e2-micro`。

```
service_name = "compute"
limit_name   = "standard-e2-micro-core-count"     # ✓
limit_name   = "standard-e2-micro"                # ✗ InvalidParameter
```

### 10. `resource_availability` 对 AD 级限额**必须**传 AD

```
service_name        = "compute"
limit_name          = "standard-e2-micro-core-count"
availability_domain = "US-ASHBURN-AD-3"           # ← 必填，不传报 InvalidParameter
```

而 `total-free-storage-gb-regional` 是区域级的，**传 AD 反而可能报错**。

### 11. AD 名带随机前缀，且**大小写不统一**

```
MKzl:US-SANJOSE-1-AD-1        ← 前缀是随机串
eu-amsterdam-1-AD-1           ← 小写区域名
US-ASHBURN-AD-3
```

**必须用 API 返回的原值，不能自己拼。** 做字符串匹配时别写死大小写。

```python
ads = client.call_all(client.identity.list_availability_domains,
                      compartment_id=tenancy)
names = [ad.name for ad in ads]
```

### 12. 实例池的子命令是 `compute-management`，不是 `compute`

SDK 里对应 `oci.core.ComputeManagementClient`，**不是** `ComputeClient`。

### 13. `instance-pool-instance` 没有 `list`

只有 `attach` / `detach` / `get` / `termination-proceed`。
要用 `list_instance_pool_instances`。

⚠️ 返回项里的 **`id` 就是实例 OCID**（不是 `instance_id` 字段）。

### 14. 🔬 `create_customer_secret_key` 的参数顺序是 `(details, user_id)`

```python
# ✗ 写反了
client.identity.create_customer_secret_key(user_id, details)
# ✓
client.identity.create_customer_secret_key(details, user_id)
```

**这个顺序跟大多数 OCI 接口相反**（多数是 `(parent_id, details)`），
很容易想当然写错。

### 15. S3 密钥：只返回一次 + 有传播延迟

**Secret Key 只在创建那一刻返回一次**，之后任何 API 都读不回来
（这是 OCI 的设计，不是权限问题）。所以「读取已有密钥」这条路不存在。

字段对应关系（实测确认）：

```
CustomerSecretKey.id   → S3 Access Key（40 位十六进制）
CustomerSecretKey.key  → S3 Secret Key（44 字符 base64）
```

**坑：新建密钥有 5~8 分钟传播延迟。** 刚创建就调用会**间歇性**报：

```
SignatureDoesNotMatch: The secret key required to complete authentication
could not be found. The region must be specified if this is not the home region.
```

实测约 5~8 分钟才完全稳定，期间同一组凭据时通时不通。
**不要据此判定密钥错误或去换映射关系** —— 加 20s 间隔重试即可。
（报错里那句 "region" 提示是误导，签名区域本来就是对的。）

### 16. botocore ≥ 1.36 的 aws-chunked 不被 OCI 支持

```
NotImplemented: AWS chunked encoding not supported.
```

（能走到这一步说明**签名已通过**，只是上传编码不兼容。）

```python
from botocore.config import Config

Config(
    signature_version="s3v4",
    s3={"addressing_style": "path", "payload_signing_enabled": False},
    request_checksum_calculation="when_required",
    response_checksum_validation="when_required",
)
```

**必须用 path-style**（`addressing_style="path"`）。

端点（两套域名等效）：

```
https://<namespace>.compat.objectstorage.<region>.oraclecloud.com
https://<namespace>.compat.objectstorage.<region>.oci.customer-oci.com
原生 API：https://objectstorage.<region>.oraclecloud.com/n/<namespace>/
```

### 17. 对象存储命名空间按**租户**共享

同一租户下的多个 user（比如号池里同一账号的两个 API key）
返回**同一个 namespace**，共享同一份 20 GiB 免费额度。

**不能按「账号数 × 20 GiB」算总量。**
判断方法：把 namespace 去重，唯一值个数才是真实额度份数。

实测 17 个账号 → 16 个唯一命名空间（其中两个账号同租户），
真实总量 320 GiB 而非 340 GiB。

### 18. `update_security_list` 是**整体替换**，不是追加

```python
# ✗ 只传改好的那条 → 会删掉 ICMP 等其它规则
client.network.update_security_list(sl_id, UpdateSecurityListDetails(
    ingress_security_rules=[modified_rule]))

# ✓ 先 get 全量、原地改目标条、再整体写回
sl = client.call(client.network.get_security_list, sl_id)
rules = list(sl.ingress_security_rules or [])
rules[idx].source = new_cidr
client.network.update_security_list(sl_id, UpdateSecurityListDetails(
    ingress_security_rules=rules))
```

**回滚也要注意**：按索引改回 `source`，而不是重建整份规则 ——
这样即使备份和当前状态之间有别的改动，也不会被覆盖。

### 19. `metadata` 可能是**显式 null**，`.get(k, {})` 挡不住

```python
# ✗ 默认值只在键「不存在」时生效，键存在但值为 None 时返回 None
metadata = launch_details.get("metadata", {})

# ✓
metadata = launch_details.get("metadata") or {}
```

这个坑让早期审计脚本对某个账号直接报
`'NoneType' object has no attribute 'get'` 而被整账号跳过。

### 20. 🔬 `oci.retry` 里**没有** `RetryStrategy` 类

```python
from oci.retry import RetryStrategy      # ✗ ImportError
from oci.retry import RetryStrategyBuilder  # ✓
```

正确用法：

```python
strategy = RetryStrategyBuilder(
    max_attempts_check=True,
    max_attempts=6,
    total_elapsed_time_check=True,
    total_elapsed_time_seconds=300,
    service_error_check=True,
    service_error_retry_on_any_5xx=True,
).get_retry_strategy()
```

`oci.retry` 里实际导出的是 `DEFAULT_RETRY_STRATEGY`（一个已构造好的实例）、
`RetryStrategyBuilder`、`NoneRetryStrategy` 和一堆
`ExponentialBackoff*RetryStrategy` 类。

### 41. Ubuntu 上 sshd 的服务名是 `ssh`，不是 `sshd`

**症状**：cloud-init 里明明写了「打开密码登录」，机器开出来**还是只能密钥登录**，
日志里一句报错都没有。用户报的就是这个。

**根因**：老格式用 `runcmd` 手写：

```yaml
runcmd:
  - echo 'root:PASS' | chpasswd
  - printf 'PermitRootLogin yes\nPasswordAuthentication yes\n' \
      > /etc/ssh/sshd_config.d/10-root-login.conf
  - systemctl restart sshd || true
```

最后一行在 Ubuntu 上必然失败：

```
System has not been booted with systemd ...        # 不是
Failed to restart sshd.service: Unit sshd.service not found.   # 是这个
```

**Debian/Ubuntu 的服务名是 `ssh`**（RedHat 系才是 `sshd`）。
而 `|| true` 把这个错误吞了 → 配置文件写好了、**sshd 从没重载** →
生效的仍然是云镜像 drop-in 里的 `PasswordAuthentication no`。

**修法**：不要自己写这套。交给 cloud-init 的 `ssh_pwauth: true` 模块，
它自己知道该重启哪个服务。

**教训**：`|| true` 用在「我不确定这步会不会失败」的地方，
等于把「失败」翻译成「成功」。要么别用，要么把错误记下来。

### 42. `chpasswd.expire` 和 `lock_passwd` 的默认值都是 `true`

**症状**：密码设了，`passwd -S` 看着也像设了，但用户首次登录
要么被强制改密码、要么干脆登不上。在**只有密码、没有键盘交互**的
自动化场景下，这看起来跟「密码不对」一模一样。

**两个默认值**：

| 键 | 默认 | 后果 |
| --- | --- | --- |
| `chpasswd.expire` | `true` | 把密码设成**已过期** → 首登强制改密码 |
| `users[].lock_passwd` | `true` | 把密码位写成 `!` → 密码不可用 |

**修法**：两个都显式写 false，并且密码走官方的 `chpasswd:` 模块
（而不是 `users:` 条目里的 `plain_text_passwd` —— 那个拿不到 `expire` 的控制权）：

```yaml
users:
- default
- name: deploy
  lock_passwd: false
chpasswd:
  expire: false
  users:
  - name: deploy
    password: 'xxx'
    type: text
```

**验证方式**：登上去跑 `passwd -S <user>`（第二列要是 `P`，不能是 `L`/`NP`）
和 `chage -l <user>`（不能出现 `must be changed`）。

### 43. `LaunchInstanceDetails` **没有** `user_data` 顶层参数

**症状**：

```
TypeError: Unrecognized keyword arguments: user_data
```

机器**根本开不出来** —— 不是「密码没生效」，是「点确认就报错」。

**根因**：OCI Python SDK 的 `LaunchInstanceDetails` 有 32 个合法参数，
**里面没有 `user_data`**（只有 `metadata` / `extended_metadata`）。
OCI 的约定是把 cloud-init 文本 base64 后放进 `metadata["user_data"]`，
和 `metadata["ssh_authorized_keys"]` 同一个字典：

```python
metadata = {"ssh_authorized_keys": pubkey, "user_data": user_data_b64}
```

**为什么拖了很久才发现**：`plan.user_data_b64` 从向导 → spec → grab → plan
一路接得都对，每一段都有测试。**只有最后一句 `LaunchInstanceDetails(**kwargs)`
是错的，而它在所有测试里都被假客户端绕过去了** ——
假客户端只记录「调用了一次 launch」，从不校验 kwargs。

**修法**：把 kwargs 拼装抽成纯函数，让**真实 SDK**去校验：

```python
oci.core.models.LaunchInstanceDetails(**_launch_details_kwargs(client, plan))
```

参数名写错就立刻 `TypeError`。不联网、不要凭据、毫秒级。
见 `tests/test_launch_details.py`。

### 44. E2 和 A1 是**两套独立限额**，挑 AD 必须带规格

**症状**：向导里选「ARM A1.Flex」，账号明明还有 ARM 余量，却报
「没有任何可用域还有额度，无法开机」。

**根因**：`standard-e2-micro-core-count` 和 `standard-a1-core-count`
是**两个互不相干的限额**。挑 AD 的代码原来只有「按 E2 算」一个口径：

```python
@property
def launchable(self) -> int:      # ← 只算 E2
    ...
```

于是账号 15 这种「**E2 已 2/2 用满、A1 还剩 2 核**」的状态下，
`pick_availability_domain()` 返回 `None` → 直接抛错 →
**A1 选项在这个账号上永远开不出机器**。

**修法**：把「能开几台」变成跟规格绑定的问题：

```python
ad.launchable_for(shape, cores)          # A1 要按台除 cores
cap.best_ad_for(shape, cores)
pick_availability_domain(cap, shape=..., cores=...)
```

**两个细节**：
- A1 必须**除以每台的核数**，否则「剩 2 核」会被当成「能开 2 台 4 核机器」
- 见 #26：A1 的额度还**不能按 AD 乘**（全区共享），两个坑要一起记

### 49. `ssh_pwauth` **改不到 root** —— `PermitRootLogin` 是编译默认值，不在你的配置文件里

**现场**（2026-09-20，`<实例公网IP>` / `oracles-15-<时间戳>`）：
向导里选了「用户名 `root` + 密码」，机器开出来后 **SSH 死活登不进去**，
`ssh -v` 只说 `Permission denied (publickey,password)`。

**第一层误导**：密码明明是设上的。
走**串口控制台**用 `root` + 同一个密码能登进去（串口绕过 sshd）。
—— 所以「密码没设上 / `chpasswd` 没生效 / `expire` 没关」这三个方向**全是错的**，
而它们每一个都「看起来很有道理」。

**真根因**：`sshd -T` 给出 `permitrootlogin prohibit-password`。
这个值**不是 cloud-init 写的** —— `/etc/ssh/sshd_config:54` 那行
`#PermitRootLogin prohibit-password` 是**注释掉的**，它是 **OpenSSH 的编译默认值**。

查 cloud-init 源码确认（别猜）：

| 键 | 实际管什么 | 源码位置 |
| --- | --- | --- |
| `disable_root` | **只**决定往 root 的 `authorized_keys` 塞不塞强制命令前缀 | `cc_ssh.py:257 apply_credentials` |
| `ssh_pwauth` | **只**改 `PasswordAuthentication` | `cc_set_passwords.py:70 cfg_name` |
| *（没有）* | `PermitRootLogin` | **cloud-init 里没有任何键写它** |

→ **必须自己写 drop-in。**

```yaml
disable_root: false
write_files:
  - path: /etc/ssh/sshd_config.d/00-oracles-root-login.conf
    permissions: '0644'
    owner: 'root:root'
    content: |
      PermitRootLogin yes
```

**时机为什么不需要重启 sshd**：`write_files` 是 `cloud_init_modules` 第 4 个，
`set_passwords` 是第 16 个，而 `cc_set_passwords.py:104` 的注释明确写着
「This module runs **Before=sshd.service**」—— sshd 首次启动时文件已在盘上。
（这也正是铁律 5 说「别用 `runcmd` 自己重启」的原因：根本不用重启。）

**两条方法论**（比这个 bug 本身值钱）：

1. **两条独立通道对照，比在一条通道上反复试错快得多。**
   「串口能登、SSH 不能登」一句话就把范围缩到 `PermitRootLogin` 了。
   如果只测 SSH，就会去怀疑密码、怀疑 `chpasswd`、怀疑 `expire`。
2. **云厂商的默认值可能根本不在你能 `cat` 到的任何文件里。**
   `sshd -T`（打印**生效值**）和 `grep PermitRootLogin /etc/ssh/**`
   （只找**文本**）会给出完全不同的答案 —— 前者才是事实。

### 50. `oci.wait_until` 返回的是 `Response`，不是资源对象 —— 一个**从没被验证过**的约定

**现场**：`open_rescue_console` 里写

```python
conn = client.wait_for_state(...)      # 拿到的是 Response
if conn.lifecycle_state != "ACTIVE":   # AttributeError
```

报错是 `'Response' object has no attribute 'lifecycle_state'`。
**`Response` 这个类名在调用点附近根本没出现过** —— 第一眼看完全不知道
它是从哪冒出来的。（当时我刚给这个函数加了「等 ACTIVE」，还以为是自己的锅。）

真相：`oci.wait_until` 把 getter 的返回值**原样递回**，而本模块
`AccountClient.call` 一律返回 `.data`。两种约定混在一起。

**为什么能潜伏这么久**：之前 3 处调用**全都丢弃返回值**——

```python
client.wait_for_state(client.compute, ..., inst.id, "RUNNING", ...)   # 返回值扔掉
```

**丢弃返回值 = 这条约定从来没被验证过。**
第一个想用返回值的人就是第一个受害者。

**判据**：一个方法有返回值、而**所有调用方都把它扔掉**时，
这个返回值等于**没有接口契约**。要么统一约定并加断言，要么明确标注「仅供副作用」。

**修法**：统一成 `.data`，与 `client.call` 对齐；
回归测试断言两个方向 ——「取得到 `lifecycle_state`」**且**「没有 `.data` / `.request`」。
只断言前者的话，返回一个既有 `.data` 又有 `.lifecycle_state` 的对象也能过。

### 53. 「默认值」是一种**安全属性**，不是一个偏好设置

**现场**：加「让 Bot 生成登录密钥」这个功能时，最自然的写法是
在点「🔑 仅 SSH 公钥」之后**直接**生成一对、注入、发文件。步骤更少。

但这会**悄悄改变默认行为**：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 私钥在哪 | **只在用户本机** | 服务器上多一份 |
| 私钥经过哪 | 哪儿都不经过 | **经过 Telegram 服务器** |
| 谁能开这台机器 | 只有持有那把私钥的人 | 加上任何拿到 VPS 或 TG 记录的人 |

用户点的是同一个按钮，**威胁模型却变了**。所以最终做成子步骤：
先问「公钥从哪来」，且**默认停在「用我配置的公钥」**上 ——
与旧版逐字节等价；「让 Bot 生成」必须用户**明确点**才发生。

**教训**：

1. 新增功能时，先问「**旧行为在什么情况下会消失**」。若答案是
   「用户什么都不做也会消失」，那这个改动必须显式化，不能当默认。
2. 「少一步」不是中性的收益 —— 它省掉的那一步如果正是**知情同意**，
   省下来的是用户的决定权。
3. 测试要**钉住默认值本身**：断言第一个按钮是 `wzk:own` 且标签里
   写着「默认」，而不是只断言「两个选项都在」。
   —— 只断言存在性的话，把两者顺序对调测试照样绿，
      而那正是这里唯一要紧的性质。

### 59. 用户可见的那一行，把**多行**信息截成了单行

**现场**（2026-09-21，用户报告）：

> 开 ARM 机器时，开机任务返回：OCI 接口返回错误：InternalError (HTTP 500)

而 OCI 的**原始信息**里明明写着 `Out of host capacity.` ——
也就是「这个 AD 现在没有物理主机」，一个**能自解释**的原因。
用户看到的是「OCI 内部错误 500」，第一反应必然是「甲骨文挂了」。

**复现**（本地，逐字符一致）：

```
用户看到的：'OCI 接口返回错误：InternalError (HTTP 500)'
用户报告的：'OCI 接口返回错误：InternalError (HTTP 500)'   ← 完全一致
```

**根因**：`describe_service_error()` 认真构造了**三行** ——

```
1. OCI 接口返回错误：InternalError (HTTP 500)
2. 原始信息：Out of host capacity.          ← 真正的原因
3. 建议：该可用域暂时没有物理容量（…）        ← 下一步怎么办
```

而 `grab.py` 里写的是 `str(exc).splitlines()[0][:200]` ——
**后两行全丢**。同一个写法在仓库里有 **9 处**。

**修法**：

1. 「取第一行」这个动作必须**显式**：新增 `errors.one_line(text, limit)`。
   名字本身就是声明「我知道这里只能放一行」；而 `splitlines()[0]`
   看起来只是「取个摘要」，很容易在用户可见的位置误用。
2. 用户可见的字段（`task.last_error`）**不截断** ——
   它会被原样渲染成「失败原因」，那里本来就允许多行。
3. 加一条 **AST 护栏**：全项目零容忍 `X.splitlines()[0]`。
   走 AST 而不是正则，因为说明这个反模式的注释和文档字符串
   里到处都有那串字面量 —— 用正则会满屏误报，而**误报会训练人去忽略它**。
4. 顺带修掉一个自相矛盾的文案：原因里已经有「建议：」时，
   结尾不再追加泛泛的「若提示额度为 0，去看配额」——
   用户会跑去查一个跟问题无关的配额（同 #38）。

**教训**：`[:N]` 和 `splitlines()[0]` 看着都是「保险地截一下」，
但**它们丢掉的正是最值钱的那部分**。判断依据不是「这个字段该多长」，
而是**「这句话是给谁看的」** —— 给用户看的字段，宁可长也不许丢信息。

### 61. 文案承诺「**每台**只试一次」，实现是「**只试一台**就停」

**现场**（2026-09-21，写抢机循环测试时撞出来的）：

汇总页对用户写的是：

> · ✅ 单次 —— **每台只试一次**，失败就收尾汇报（不空转烧 API）

`run_grab_loop` 的 docstring 也写着「``one_shot=True``（单次开机）：
**每台**只试一次，失败就收尾汇报」。三处文案（含按钮标签）口径一致。

而实现是：

```python
        if task.done_count >= task.want:
            task.status = "succeeded"
            break

        one_shot = not task.spec.get("retry")
        if one_shot:
            task.status = "stopped"      # ← 无条件 break，不管这一轮成没成
            break
```

于是「选 **3 台** + 现在开机」→ 只开出 **1 台**，
然后给用户看「⚠️ 部分成功（1/3 台）· 可改用自动抢机继续补齐」。

**怎么发现的**：给 `run_grab_loop` 补测试（这个函数当时**一条测试都没有**），
写 `test_a_partial_success_keeps_going` 时断言「该被调用 2 次」，
实际只调用了 1 次。**测试的期望值是从文案抄来的** —— 于是文案和实现
的差异被自动暴露出来了。

**修法**：单次模式改成「成功一台就接着开下一台，一旦某台失败才收尾」。
「不空转烧 API」的意思是**失败不重试**，不是**只试一台**。

**教训**：

1. **文案是一种规格。** 三处文案口径一致而实现是少数派时，
   先假设**实现**错了 —— 这次就是。
2. 期望值**从文案抄**（而不是从实现抄）是有意的：
   从实现抄来的期望值只能锁住现状，抄文案才能发现「说的和做的不一样」。
3. 一个**零测试覆盖**的函数，它的行为没人知道 ——
   包括它的作者。这个 bug 和 #59 在同一个函数里，
   而它在用户报告之前从没被任何测试碰过。

### 21. 22 端口对全网开放是**默认行为**

实测 17/17 个账号全部命中。这是 **OCI 建 VCN 时自动生成的
`Default Security List` 默认规则**，不是用户手动配的。

**所以「我没配过安全组」≠「22 端口是关的」。**

**判定端口是否被覆盖**：`tcp_options.destination_port_range` 为 `None`
表示**全端口**；协议 `all` 也算覆盖。

⚠️ 必须同时扫**安全列表和安全组(NSG)** —— 只查安全列表会漏掉 NSG。

### 22. `bucket-count` 计数可能滞后

实测某账号 `bucket-count` 显示已用 1，但实际列出 0 个桶。
这是 OCI 的限额计数器滞后，**不影响可用性**，但会让「配额说有多少桶」
和「桶列表实际有多少」对不上。

**以 `list_buckets` 的结果为准。**

### 23. 实例刚 `RUNNING` 时 SSH 连不上

报的是 **`Connection refused`（不是 timeout）** —— 那是 cloud-init/sshd
还没就绪，等约 1 分钟即可。

**不要误判成安全组问题。** 如果是安全组问题，表现是 timeout 而不是 refused。

### 24. `list_images` **必须**带 `shape`

```python
client.compute.list_images(compartment_id=tenancy, shape="VM.Standard.E2.1.Micro",
                           operating_system="Canonical Ubuntu",
                           sort_by="TIMECREATED", sort_order="DESC")
```

不带 `shape` 会列出该 OS 下所有镜像，包含跟这个规格**不兼容**的，
挑错了 launch 会失败。

### 25. `list_instances` 会返回已销毁的残留记录

`lifecycle_state == "TERMINATED"` 的实例仍会出现在列表里。
不过滤的话列表里全是幽灵。

`standard-a1-core-count` 在每个 AD 都显示剩 2 核、used 0，

按「每 AD 2 核 × 3 AD = 6 核」算会**严重高估**。

### 45. 顶层别写 `version` —— 但理由不是「会报错」

**先把事实说准**：`version: v1` **不会报错、也没有警告**。

2026-09-20 用 `cloud-init schema --config-file` 实测：

| 配置 | 结果 |
| --- | --- |
| `#cloud-config` + `version: v1` | `Valid schema` |
| `#cloud-config` + `version: v999zzz`（瞎写） | `Valid schema` |
| `#cloud-config` + `totally_unknown_module: {...}` | **`Invalid user-data`** |

原因：cloud-init 的 `schema-cloud-config-v1.json` 里 `version` 就是 `"version": {}`
—— **空 schema，等于不校验**。所以它既不报错也不起作用。

**删掉它的理由是「去掉误导」**：它不产生任何效果（没有任何模块读它），
留着会让人误以为它和 `#cloud-config` 头一起构成某种「版本声明」。

> **这条差点被我写错。** 我原本写的是「会被当成 unknown key 报警告」，
> 是在做**对照组实验**（拿一个真的错的配置去撞同一个校验器）时
> 才发现校验器认得 `version`。
> **教训**：下「X 会报错」这种结论前，先让 X 和「一个真的错的 Y」都过一遍
> 同一个检查 —— 只看到「X 没报错」说明不了任何事，
> 要看到「Y 报错了」才知道这个检查有鉴别力。

### 46. 内联键盘的行宽是**等分**，标签长了会被截断

**症状**（用户原话）：「抢机设置的秒数显示不出来，我只看到『自动抢...』」

**根因**：Telegram 内联键盘**占满消息宽度**，一行 n 个按钮各占 `W / n`
（**不是**按内容自适应）。4 个间隔按钮塞一行 → 每格只剩约 9 个半角单位
→ 标签 `🔄 自动抢机 5s` 被截断，而**被吃掉的正好是唯一有意义的信息（秒数）**。

怎么确定是「等分」而不是「按内容自适应」：若是后者，那一行 4 个按钮本身
就是最宽的一行 → 反而不会被截断，与用户看到的现象矛盾。

**修法二选一**：① 缩短标签；② 把它单独放一行（独占整行宽度）。

**顺带撞出来的同类问题**：`4 OCPU（免费上限）`、`50 GB（默认）`、
`🔁 重体检（含 API）`、`🚑 救援（串口 / VNC）`、`🔑 签发 S3 密钥` ×2 ——
一共 6 处。所以别只修用户报的那一处，**写个宽度不变量把所有键盘都过一遍**
（见 `tests/test_keyboards.py`）。

**这个 bug 的性质**：不报错、不崩溃、功能也还在，只是**用户看不到自己在选什么**。
属于静默失效家族，只有断言能拦住。

### 48. `BOOT_VOLUME_GB = 47` 已经过时 —— 默认开机路径 100% 失败

**症状**（真机验证时撞出来）：

```
InvalidParameter (HTTP 400)
Requested volume size 47GB is not in the allowed range.
Boot volume should be greater than or equal to 50GB
and less than or equal to 32,768GB.
```

**根因**：`models.py` 里的 `BOOT_VOLUME_GB` 是 **47** —— 这是**历史值**，
存量实例的引导卷确实都是 47 GB，所以它「看起来是对的、一直没被质疑过」。
但 **OCI 现在的下限是 50 GB**，新开机时 47 必被拒。

**为什么这么难发现**：

| 路径 | 传的磁盘大小 | 结果 |
| --- | --- | --- |
| 向导里显式选「50 / 100 / 200 GB」 | 50 / 100 / 200 | ✅ 正常 |
| 向导里选「默认」 | 不传 → 用 `BOOT_VOLUME_GB` = 47 | 🔴 **必被拒** |

也就是说**只有「默认」这一条路死掉**，而它恰好是最常走的那条。
更坑的是：`BOOT_VOLUME_GB` 同时还是**容量公式里的分母**
（`块存储余量 // BOOT_VOLUME_GB`），所以它既影响「能不能开」，
又影响「还能开几台」—— 改它要同时想清楚这两件事。

**修法**（两层，缺一不可）：

1. 常量改 `50`，并**单独定义** `BOOT_VOLUME_MIN_GB = 50` 表示「OCI 的硬下限」
   —— 把「我们的默认值」和「API 的约束」分成两个概念，
   下次 OCI 再抬下限时，改的是下限、不是默认值
2. `plan_launch()` **开头就拦**：`boot_volume_gb < BOOT_VOLUME_MIN_GB` → 抛人话

```python
raise ValueError(
    f"引导卷 {boot_volume_gb} GB 低于 OCI 的下限 {BOOT_VOLUME_MIN_GB} GB。\n"
    f"  OCI 会直接拒：Requested volume size {boot_volume_gb}GB is not in the allowed range.\n"
    f"  请用 ≥ {BOOT_VOLUME_MIN_GB} GB（向导里的 50/100/200 都是合法的）。"
)
```

第 2 层不是重复劳动：**在计划阶段报错**和**等 OCI 甩 400** 的差别是
「用户看到一句中文说明」vs「用户看到一串 OCI 话术，不知道是自己选错了
还是我们代码有 bug」。所有能从 API 约束推导出来的前置校验，
都应该放在**只读的计划阶段**，而不是留给服务端拒绝。

**这条的元教训**：**「历史值」会随 API 演进而失效，而它看起来永远是对的。**
存量实例是 47 GB，所以 47 这个数字有实物佐证 —— 但它描述的是**过去**。
凡是「写死的、跟外部系统约束有关的常量」，都要有一条**断言它仍然合法**的测试
（这里是 `test_boot_volume_constant_matches_reality`），
而不只是「断言它等于某个数字」。

## 🧯 元坑：让「检查」本身失效的坑

> 下面这几条不是 OCI 的坑，是**写检查程序时**踩的坑。
> 单独分一节，因为它们比业务坑更危险 ——
> 业务坑会让功能出错（你能看见），
> 这类坑会让**你以为一切正常**（你看不见）。
>
> 共同特征：**检查在跑，输出全绿，但什么也没检查。**

### 27. 把「扫描失败」写成「什么都没有」

一开始批量扫描的 `on_error` 写的是：

```python
on_error=lambda c, exc: []      # ❌ 失败 = 空列表
```

后果：某个账号密钥过期时，它被渲染成「该账号很干净」。

- 计费审计里 → 漏掉**正在持续扣费**的未绑定公网 IP
- 安全审计里 → 漏掉**对全网开放**的 22 端口
- 而且**完全不报警**，报告上一切正常

这和业务侧第 5 条（「空桶」和「查询失败」必须是两个结果）是同一个病，
只是换了个地方发作。

**正确做法**：用 `None` 表示「结果未知」，和 `[]`（确实没有）严格区分：

```python
from oracles.services import scan_failed    # 固定返回 None
on_error=scan_failed
```

渲染层会把失败的账号单独列出来，并且措辞跟着失败数走 ——
有账号没扫成功时只能说「已扫到的部分没问题」，不能说「整体没问题」。

`tests/test_scan_failure_semantics.py` 锁住了这个语义。
里面还有一个**源码级接线检查**：光有渲染层的测试不够，
因为有人把调用方改回 `lambda c, exc: []` 时，渲染层永远收不到 `None`，
那些测试照样全绿。所以直接扫源码禁止这种写法。

### 28. `git diff --name-only` 转义了非 ASCII 文件名

`--staged` 模式要拿暂存文件列表，写的是：

```bash
for f in $(git diff --cached --name-only); do
    [ -f "$f" ] || continue      # ❌ 中文名文件全被跳过
```

`git` 默认 `core.quotepath=true`，非 ASCII 路径会被转义成
`"docs/01-\345\277\253..."` 这种**带引号的字面量**。
拿它去 `[ -f "$f" ]` 永远为假 → `continue` → **静默跳过**。

本项目 6 份文档全是中文名，等于一直没被扫过。
更糟的是扫描器仍然打印「✓ 暂存内容干净」。

**正确做法**：

```bash
git -c core.quotepath=false diff --cached --name-only --diff-filter=ACM -z
# 配 while IFS= read -r -d '' 按 NUL 切分（顺便解决路径含空格的问题）
```

并且加了兜底：暂存区有 N 个文件却一个都读不到时**直接报错**，
而不是假装扫描通过。

### 29. 同一份检查有两处实现，必然漂移

CI 的 `.github/workflows/secret-scan.yml` 里内联复制了一份密钥扫描规则，
和本地 `scripts/check_secrets.sh` 各写各的。结果：

- CI 的白名单里残留着 `aaaa`（见第 30 条），OCID 检查形同虚设
- CI 的规则比本地少 2 条（私钥文件名、疑似 SecretKey）

本地改了，CI 没改，两边说的不是一件事。

**正确做法**：CI 直接调用仓库里的脚本，不复制规则。
扫描器是唯一事实来源。`同一份检查有两处实现，就一定会分叉。`

### 30. `PATH` 上的 grep 可能不是 GNU grep —— BRE 的 `\|` 交替会静默失效

写验证命令时用了：

```bash
grep -n 'ocid1.instance\|ZZZfakeToken\|9876543210:' file    # ❌ 匹配不到，exit 1
```

**这句「确认文件已还原干净」的验证命令自己失效了**，
于是它报告「干净，无残留」而文件里明明还残留着测试数据。

2026-09-20 查实了根因 —— 不是「macOS 的 BSD grep 不可靠」，
而是**本机 `PATH` 上的第一个 grep 是 toybox**：

```console
$ which -a grep
/Applications/WorkBuddy AI.app/.../shim/brokered-bin/grep   # ← toybox
/usr/bin/grep
$ grep --version | head -1
toybox 0.8.13 (is not GNU grep 9.0)
```

toybox 的 BRE 不支持 `\|`，而且**不报错** —— 只是返回「无匹配」，退出码 1。
实测同一个文件：

| 写法 | 结果 |
| --- | --- |
| `grep -c "rsync" file` | `6` ✅ |
| `grep -cE "egg-info\|rsync" file` | `9` ✅ |
| `grep -c "egg-info\|rsync" file` | `0`，exit 1 ❌ |

**最坏形态是闸门**：`if grep -q "a\|b" file; then die "发现敏感信息"; fi`
→ 匹配不到 → 条件为假 → **闸门静默放行**，日志里一切正常。

（同一类问题的另一个版本：ERE 模式下的 `\b` 也是这里不支持的，
见 `scripts/check_secrets.sh` 里的注释 —— 那个 bug 让 Telegram Token 检查
**一直静默失效**。）

**正确做法**：
- 用 `grep -E` 显式走 ERE，或用 `grep -F` 精确匹配
- 多模式就分多次调用，别赌 `\|`
- 换环境后先跑一次体检：`printf 'a\nb\n' > /tmp/_g && grep -q 'a\|b' /tmp/_g || echo "这台机器的 grep 不支持"`，
  并用 `grep --version | head -1` 确认到底是谁
- **凡是"验证某件事"的命令，先验证它自己**（`check_secrets.sh --verify` 就是这个思路）

### 31. `python -m pytest` 能跑，`pytest` 不能

```bash
python -m pytest tests/    # ✅ 能 import oracles
pytest tests/              # ❌ ModuleNotFoundError
```

`python -m` 会把**当前工作目录**塞进 `sys.path`，裸 `pytest` 不会。
于是本地跑得好好的，CI 上换了个调用方式就炸。

CI 里通常有 `pip install -e .`，所以 `import oracles` 没问题 ——
但**测试辅助模块**（比如 `tests/telegram_harness.py`）装不进包里，
换调用方式就 ImportError。

**正确做法**：仓库根放一个 `conftest.py` 把根目录加进 `sys.path`。
pytest 收集时会先加载它，三种调用方式就都一致了：

```python
# conftest.py
import sys
from pathlib import Path
ROOT = Path(__file__).resolve().parent
if str(ROOT) not in sys.path:
    sys.path.insert(0, str(ROOT))
```

### 32. 写 handler 测试时，假对象过不去 `isinstance` 检查

`on_error` 里有 `isinstance(update, Update)`，用假 `Update` 测就永远走不进
「回消息」那条分支 —— 测试看着过了，其实什么都没验证。

而 PTB 的类都定义了 `__slots__`，**没法给实例挂属性**：

```python
msg.reply_text = fake_reply      # ❌ AttributeError: 'Message' object has no attribute
monkeypatch.setattr(Message, "reply_text", fake_reply)   # ✅ 只能在类上打桩
```

**教训**：假对象和真对象混用时要小心 —— 凡是代码里有 `isinstance` 检查的地方，
假对象就走不到那条分支。这类测试要给假对象加断言（「确实调用了」），
而不是只看「没抛异常」。

### 33. 部署脚本无条件启动服务 → 凭据没填就报「安装失败」

`install.sh` 原来是这么收尾的：

```bash
systemctl enable oracles-bot
systemctl restart oracles-bot
sleep 3
if systemctl is-active --quiet oracles-bot; then ... else exit 1; fi
```

unit 里是 `Restart=always` + `RestartSec=10`。而 `python -m oracles` 走
`load_settings()`，默认 `require_token=True` —— **Token 为空就抛错退出**。

于是「先装、后填凭据」这条完全正常的路径变成：

1. 进程立刻退出 → systemd 每 10 秒拉一次 → 无限崩溃循环，journal 被刷爆
2. `is-active` 查到的是 `activating`（自动重启中的状态），**不算 active** → `exit 1`
3. 用户看到红字「安装失败」，以为整个装挂了

而真相是：**代码、依赖、`/etc/oracles`、systemd unit 全都已经就位，只差两行凭据。**
一个正常的部署流程被报成了失败。

修法是把「装好」和「启动」拆成两件事：

```bash
if [ "$TOKEN_OK" -eq 1 ] && [ "$IDS_OK" -eq 1 ]; then
    systemctl enable oracles-bot >/dev/null
    systemctl restart oracles-bot
    ...
else
    systemctl disable oracles-bot >/dev/null 2>&1 || true
    systemctl stop oracles-bot >/dev/null 2>&1 || true
    warn "Telegram 凭据还没配好，服务已安装但**未启动**"
fi
```

**顺带踩到的第二个坑：判「非空」而不是判「形态」。**

`deploy/oracles.env.example` 里写的是 `TELEGRAM_BOT_TOKEN=在这里填BotFather给的token`
—— 这个值**不是空的**。所以 `[ -n "$TOKEN" ]` 会放行一句占位文字，
服务照样起来照样崩，白改。

必须校验形态，正则和 `oracles/redact.py` 保持一致：

```bash
grep -Eq '^[0-9]{8,12}:[A-Za-z0-9_-]{30,45}$'   # token
grep -Eq '^[0-9]+(,[0-9]+)*$'                   # 用户 ID
```

⚠️ 写这个判断时注意 `set -e` 的经典陷阱：

```bash
cmd | grep -Eq '...' && OK=1     # ❌ grep 失败时整个 AND-OR 列表返回非零 → 脚本直接退出
if cmd | grep -Eq '...'; then OK=1; fi   # ✅
```

**教训**：安装脚本的「成功/失败」结论必须是可信的。只要它可能把
「还差一步配置」报成「装挂了」，用户就会开始忽略它的输出 —— 那这个脚本
就退化成了一个必须人工复核的脚本。**部署脚本宁可少做一步，也不要说错一句话。**

### 34. Ubuntu 26.04 的 `python3` 不带 `ensurepip`，而且 apt 索引是空的

在一台全新的 OCI Ubuntu 26.04 实例上跑 `install.sh`，第 2 步直接挂：

```
The virtual environment was not created successfully because ensurepip is not
available.  On Debian/Ubuntu systems, you need to install the python3-venv
package using the following command:

    apt install python3.14-venv
```

照着做，又是一闷棍：

```
E: Package 'python3-venv' has no installation candidate
E: Package 'python3.14-venv' has no installation candidate
```

两个坑叠在一起：

| 坑 | 说明 |
| --- | --- |
| **包名带版本号** | 系统 `python3` 是 3.14.4，但包叫 `python3.14-venv`，不是 `python3-venv` |
| **apt 索引是空的** | 云镜像由 cloud-init 首次启动生成，`/var/lib/apt/lists` 没拉过。**不先 `apt-get update` 就永远 "no installation candidate"** |

官方那句报错**两个关键点都没说** —— 它给的包名装不上，也没提先 `update`。
用户会卡在「照着提示做还是不行」的死循环里。

修法是在**第 2 步之前**加预检（见 `install.sh` 第 0.5 节）：

```bash
if ! python3 -c 'import ensurepip' 2>/dev/null; then
    PYVER="$(python3 -c 'import sys; print("%d.%d" % sys.version_info[:2])' 2>/dev/null || echo 3.x)"
    warn "python3 缺少 ensurepip 模块，建不了 venv。"
    cat <<EOF
  修复（注意包名带版本号）：
      sudo apt-get update
      sudo apt-get install -y python3-venv python${PYVER}-venv
EOF
    die "装完上面的包再重新执行本脚本"
fi
```

**为什么必须前置**：原来自检是放在第 2 步里的。那时 `oracles` 用户、`/opt/oracles`、
rsync 副本都已经建好了 —— 失败会留下半装状态。现在它在**任何破坏性动作之前**就停。

**写这段预检时自己踩了两个坑**（都用打桩测试抓出来了，见下）：

```bash
PYVER="$(python3 -c '...')"        # ❌ set -e 下命令替换失败 → 整个脚本静默退出，
                                   #    连下面那句 warn 都执行不到，用户只看到一片空白
PYVER="$(python3 -c '...' || echo 3.x)"   # ✅
```

```bash
sudo apt-get install -y python3-venv python3${PYVER}-venv   # ❌ PYVER 已含 "3."
                                                            #    → python33.14-venv（不存在的包）
sudo apt-get install -y python3-venv python${PYVER}-venv    # ✅ python3.14-venv
```

**教训**：安装脚本的**前置检查本身也要被测**。这次用假 `python3` + 假 `id`
（骗过 root 检查）在临时目录里把脚本跑起来，断言三件事：
① 提示里出现 `ensurepip` 和 `apt-get update`；② 包名拼对；
③ **输出里不能出现「创建系统用户」「同步代码到」** —— 最后这条才是在验证"时机"，
前两条只验证"内容"。光看提示写得对不对，会漏掉整个预检块因为 `set -e` 而空转的情况。

### 35. 把开源安全托付给第三方扫描器 + 它不认识你的约定

CI 里挂了 `gitleaks/gitleaks-action@v2`，看着很专业。**实测下来它几乎什么都没抓到。**

往源码里注入 7 类本项目的真实密钥，两组扫描器对照：

| 密钥类型 | `check_secrets.sh` | gitleaks |
| --- | :---: | :---: |
| Telegram Bot Token | ✅ | ❌ |
| OCI OCID（user / tenancy） | ✅ | ❌ |
| API 指纹 | ✅ | ❌ |
| PEM 私钥 | ✅ | ✅ |
| S3 AccessKey | ✅ | ❌ |
| 私钥文件路径 | ✅ | ❌ |
| 疑似 SecretKey | ✅ | ❌ |
| **合计** | **7/7** | **1/7** |

**原因**：gitleaks 的默认规则集是按「通用密钥形态」设计的 ——
它不认识 `ocid1.` 这种厂商特有前缀，也不认识 Telegram 的 `<数字>:<35位>` 形态。
而这两样恰好是本项目**最要命**的两类密钥。

> **一个只覆盖你威胁模型 1/7 的扫描器，会让你以为自己在被保护。**
> 它最大的危害不是漏检，是让你**不再写自己的扫描器**。

**同一件事还有第二面：它不认识你的约定。**

仓库里有 5 处 token 形态的字符串（测试夹具 + 扫描器自检样本），
本地脚本用行内标记 `secret-scan:allow` 放行。但 gitleaks 不认识这个标记 ——
于是它每次都报，CI 每次都红。

**而一个红久了的检查等于没有检查。** 大家会开始无脑忽略它，
真泄露混在一堆假警报里根本看不出来。

修法：仓库根目录加 `.gitleaks.toml`，把本仓库已判定为虚构的东西**精确翻译**过去：

```toml
[extend]
useDefault = true          # 继承默认规则，只在其上做豁免

[[allowlists]]
description = "扫描器自身与编译产物"
paths = ['''^scripts/check_secrets\.sh$''', '''__pycache__/''']   # 与 SKIP_FILES 保持一致

[[allowlists]]
description = "行内标记（与本地脚本同一个字符串）"
regexTarget = "line"       # 在命中所在行里找标记，而不是只看命中片段
regexes = ['''secret-scan:allow''']
```

⚠️ **不能**加 `EXAMPLE` / `example` 这类通用 allowlist —— 真实凭据完全可能
带这些字样，放行就等于给泄露开口子。豁免必须精确到「文件」或「行」。

**顺带发现的第三个问题：步骤顺序是反的。**

原来 CI 把 gitleaks 排在第一步。但 GitHub Actions 一旦某步失败就**中止后续步骤**
—— gitleaks 报一个假阳性，真正的主闸门 `check_secrets.sh` 就**根本不会运行**。
顺序调成：先自检规则 → 再跑自己的扫描器 → 最后才是 gitleaks 兜底。

**教训：检查的排列顺序本身就是一种设计决策。** 把弱检查排在强检查前面，
等于用弱检查的假阳性把强检查屏蔽掉。

**验证豁免没有把自己变成橡皮图章（必做）**：改完 `.gitleaks.toml` 后，
往任意源码文件注入形态真实的密钥，**做对照组实验** —— 分别用默认配置和
自己的配置扫同一个文件：

```python
d = scan(use_my_config=False)   # 默认配置命中了吗
m = scan(use_my_config=True)    # 我的配置命中了吗
if d and not m:
    print("❌ 我的豁免吃掉了原本能命中的检测")   # ← 只有这一种才是真问题
elif not d and not m:
    print("⚠️ gitleaks 本来就不认（与配置无关）")  # ← 别误判成自己写错了
```

**这个对照组是关键**：只看「加了配置之后扫不出来了」，会分不清
「配置写对了」和「规则本来就抓不到」。前者是好事，后者说明主闸门缺位。
不做对照就会得出完全相反的结论。

#### ⚠️ 对照组自己踩了三个坑（比结论更值得记）

**坑 1：变量没真的去掉。** 「不带 `--config` 跑一次」**不能**当基线 ——
gitleaks 会**自动发现**源目录里的 `.gitleaks.toml`，两次用的是同一份配置，
对照根本没成立。第一版实验就是这么错的，还差点据此写下「已验证」的结论。

```bash
# ❌ 假的基线：仍然读到了 .gitleaks.toml
gitleaks detect --source . --no-git
# ✅ 真的基线：把配置文件从副本里删掉
cp -r repo /tmp/baseline && rm /tmp/baseline/.gitleaks.toml
```

> **对照组必须真的把变量去掉，而不是「换个方式调用」。**
> 先确认「有变量」和「无变量」时结果确实不同，再谈结论。

**坑 2：过滤器匹配到了不该匹配的东西。** 用 `endswith("redact.py")` 过滤命中，
连 `tests/test_redact.py`（里面本来就有 PEM 夹具）一起命中了 ——
每个用例都显示 `private-key`，对照结果全错。
**过滤条件必须精确到「你注入的那个文件」，用完整路径，别用模糊后缀。**

**坑 3：用规则名判定，而不是命中条数。** 要验证的性质是
「标记只豁免那一行，不放行整个文件」—— 这是**计数**问题。
必须比条数，再补一条**顺序颠倒**的用例（带标记的行放前面），
证明它不是「文件里出现一次标记就整份放行」：

```python
# 同一文件里：1 个无标记 + 1 个带标记
assert baseline_count == 2      # 基线两条都抓到
assert configured_count == 1    # 加了配置只豁免掉带标记那条
```

最终 5/5 用例通过，才算真的验证完。

### 36. 日志读起来像「执行过」，比没有日志更危险

真机部署后翻 journal，看到这么一条：

```
23:12:19 INFO oracles.bot.dispatch   执行待确认操作 kind=launch account=3 user=1447289689
```

然后**没有了**。既没有「已执行」，也没有「已拒绝」，更没有报错。

去看代码才发现原因：

```python
log.info("执行待确认操作 kind=%s account=%s user=%s", ...)
try:
    return await handler(pending, settings, registry)
except NotAllowedError as exc:
    return str(exc)          # ← 写开关拦下时**直接返回，不打任何日志**
```

用户确实在 Telegram 里收到了「🔒 写操作已禁用」的拒绝消息（功能是对的），
但**服务端日志里查不到这件事发生过**。

两个问题叠在一起：

| 问题 | 后果 |
| --- | --- |
| 被拦下的写操作不留痕 | 「谁在什么时候试图做什么、有没有被拦住」—— 运维最需要的信息没了 |
| 意图日志写的是「执行待确认操作」 | 读起来像**已经执行了**，实际什么都没发生 |

**对一个管云基础设施的工具来说，第二点比第一点更严重。**
没有日志你知道要小心；**有日志但读起来像执行过，你会基于错误的事实做判断**
—— 比如以为机器已经开了，去查为什么连不上。

修法是让每条日志都明确表态：

```python
who = f"kind={pending.kind} account={pending.account_index} user={pending.user_id}"
log.info("收到执行确认（尚未执行）：%s", who)
try:
    result = await handler(pending, settings, registry)
except NotAllowedError as exc:
    # 被写开关拦下 —— 这是安全事件，必须留痕
    log.warning("写操作被拒绝：%s —— %s", who, str(exc).splitlines()[0])
    return str(exc)
except Exception as exc:
    log.exception("执行 %s 失败", pending.kind)
    return f"❌ 执行失败：\n{str(exc)[:800]}"
log.info("执行完成：%s", who)      # 走到这里才是真的执行了
return result
```

**「执行完成」放在 try 外面是有依据的**：7 个 `_do_*` 全部以
`ensure_writable(...)` 开头，所以「没抛异常」等价于「写开关是开的、动作已下发」。
这个不变量值得写进注释 —— 否则以后有人加一个不调 `ensure_writable` 的
handler，这条日志就会开始撒谎。

**顺带补了 3 条测试**（`caplog`）：
① 被拦下必须产生 WARNING，且带 kind/account/user；
② 意图日志必须含「尚未执行」，且被拦下时**不能**出现「执行完成」；
③ 真执行成功必须留痕（否则拦截日志无从对照）。

同样用变异测试验证：**4/4 拦住**（完全退回旧写法 / 只去掉拒绝日志 /
只把措辞改含糊 / 只去掉成功留痕）。

**教训**：日志不只是「出问题时给你线索」，它还是**事实来源**。
任何一条会被读成「事情发生了」的日志，都必须能证明事情真的发生了。
**宁可多打一行，也不要让人误判。**

### 37. 「🚑 救援」按钮从来没真正跑通过 —— `publicKey` 必填，而且只收 RSA

2026-09-20 生产日志：

```
oracles.errors.OciApiError: OCI 接口返回错误：InvalidParameter (HTTP 400)
原始信息：publicKey must not be null
```

点「🚑 救援」只回一句报错。**两处错误认知叠在一起**：

1. `open_rescue_console` 把 `public_key` 当**可选**参数，不传就发请求。
   而 OCI 的 `create_instance_console_connection` 要求它**必填**。
2. 就算传了，也**只收 RSA**。实测（sa-vinhedo-1）：

   | 公钥类型 | 结果 |
   | --- | --- |
   | `ssh-ed25519` | ❌ `Invalid ssh public key type "ssh-ed25519"` |
   | `ssh-rsa` | ✅ 接受 |

   而项目里那把开机用的公钥正好是 ed25519 —— 顺手复用会直接撞墙。

**同一段代码的第三个错误**：`render()` 告诉用户
「装个 VNC 客户端（RealVNC / TigerVNC），把上面连接串粘进去即可」。
但真实返回的是**一条 SSH 命令**：

```
ssh -o ProxyCommand='ssh -W %h:%p -p 443 <conn-ocid>@instance-console.<region>.oraclecloud.com' <instance-ocid>
```

不是 `vnc://` 链接，VNC 客户端根本粘不进去。

**这三个错误共同说明一件事：这段代码从来没被执行过一次**，是照着想象写的。
字段名对得上、类型对得上、测试也绿 —— 但一次都没真跑过。

**正确做法**：
- `publicKey` 必填。不传就现场生成一对临时 **RSA-2048**，
  把**私钥**回给用户（连接串是 SSH 命令，没私钥进不去），并渲染进命令里
  （`ssh -i oracles-rescue.pem …`，别让用户自己找 `-i` 插哪儿）
- 已有旧连接时：用户自带公钥 → 复用；现场生成的 → **删掉重建**。
  否则旧连接是用**别的**公钥开的，用户拿着新私钥进不去
- 想不经过 Telegram 传私钥，就配 `ORACLES_CONSOLE_PUBLIC_KEY`（必须 ssh-rsa）
- 停机实例开不了救援 —— 按钮**干脆不显示**，别亮一个点了必然报错的键

### 38. 同一个功能两个入口，只测了一个

`/terminate` 命令走 `cmd_terminate`（有测试、是好的）；
点「🗑 销毁」按钮走 `_power_plan`（没测试、**是坏的**）。
两条路通向同一个服务函数，但只有一条被覆盖。

按钮那条路上还有一段**永远走不到的死代码**：
`plan_power` 的校验排在 `terminate` 分支**之前**，
而 `plan_power` 只认 `POWER_ACTIONS`，传 `"terminate"` 直接抛 `ValueError`。
于是点按钮只会看到：

```
❌ 未知动作 'terminate'，可选：['reboot', 'reset', 'softstop', 'start', 'stop']
```

**为什么没被现有测试抓到**：`test_every_main_menu_button_is_handled` /
`..._account_picker_...` 覆盖了主菜单和账号选择器，**唯独漏了实例菜单**；
而且它们只断言「没有『未知操作』提示」—— 那是**路由**层面的检查。
这个 bug 的路由是通的（`ip:` 分支接住了），是**动作本身**跑不通。

**正确做法**：
- 遍历按钮时**从真实键盘对象取 `callback_data`**，不要硬编码前缀。
  （硬编码 `im:` 会打开实例菜单而不是执行动作 —— 菜单渲染成功、没有报错，
  于是测试报「通过」，测的根本不是想测的东西。）
- 判据从「没有『未知操作』」升级为「回话里不能出现 ❌ **且不能为空**」。
  **空回话必须算失败**：被白名单挡掉、路由没接住时一个字都不回，
  而「不含 ❌」在空字符串上恒为真。
- 对每个动作再断言「真的产出了待确认操作」，而不只是「没报错」。

### 39. 桩打得太高，会把被测行为一起桩掉

复现 terminate bug 的第一版测试**「通过」了** —— 因为我把 `plan_power`
本身也 monkeypatch 掉了，而那正是抛异常的函数。

同一个错误在救援上也犯了一次：`_stub_instance_services` 里桩掉了整个
`open_rescue_console`，于是「不传必填的 `publicKey`」在测试里完全看不见。

**正确做法**：
- **只桩最下层**（网关 / 网络边界），让被测函数整段真跑。
  本项目为此在 `tests/telegram_harness.py` 里做了一个假 OCI 网关
  （`FakeClient` + `FakeComputeNamespace`），能记录请求参数供断言。
- 判据：**如果被测函数内部随便改坏，这条测试会红吗？** 不会红就是桩太高了。
- 拿不准就做**变异测试**：把代码改回有 bug 的形态，看测试是否变红。
  2026-09-20 用这招验证了 4 个变异体全部被抓住。

### 40. 别从**被截断的输出**里推断结论

- 统计数字要**看到**才算数；被 `tail`/`head` 截断的输出里没有结论
- 报「通过」的判定必须能区分「干了事」和「什么都没发生」
- 关键数字用**独立方法复核**（这里是导出一份索引副本单独跑）


### 47. 「逐段读代码，接线都对」是一个**不可能失败**的检查

这是本轮最贵的一课。

排查「用户名密码没生效」时，我把链路逐段读了一遍：

```
_wz_build_spec()  → spec["user_data_b64"]  ✓ 有
grab.py           → plan.user_data_b64     ✓ 接上了
execute_launch()  → details_kwargs[...]    ✓ 看起来也对
```

于是写下结论：**「接线是正确的，问题在旧格式的 cloud-init」**。

然后真开一台机器，SDK 直接甩脸：

```
TypeError: Unrecognized keyword arguments: user_data
```

**这一段里唯一错的地方，恰好就是我没法靠读代码判断的那一步** ——
`LaunchInstanceDetails(**kwargs)` 到底认不认 `user_data` 这个键。
「看起来对」的代码，在参数名拼错时和正确代码**长得一模一样**。

**为什么现有测试全绿**：所有测试都用假客户端，
假客户端只记录「调用了一次 launch」，**从不校验 kwargs**。
于是这个错误在测试里是**不可观测**的。

**判据**：问自己「**这个检查有没有可能失败？**」

- 「读代码看接线对不对」→ 答案永远是「对」→ **不是检查**
- 「把 kwargs 喂给真实 SDK」→ 拼错就炸 → 是检查
- 「真开一台机器，用密码登进去」→ 最贵但最真

同类现象在 #39（桩打在被测函数上）、#40（从截断输出推断）都出现过。
共同点：**检查跑过了，但它在结构上不可能给出「否」**。

**可复用的做法**：
1. 能喂给真实依赖校验的，就别用假对象（这里是 SDK 的模型构造器）
2. 假对象要**校验入参**，不能只记录「被调用了」
3. 最后一定要有一次**端到端真跑** —— 它专门抓「每段都对、拼起来错」的那类 bug

### 51. 「先到先得」只在**存在竞争者**时才咬人 —— 差点把局部观察推广成通用规律

**背景**：要给 root 写 `PermitRootLogin yes` 的 sshd drop-in，
文件名前缀用多少？当时我「知道」一个规律：

> OpenSSH 对同一关键字只取**第一个**出现的值，drop-in 按文件名字典序加载，
> 所以必须用 `00-`，用 `99-` 会被 `60-cloudimg-settings.conf` 吃掉。

听起来完全正确，而且**铁律 2 里的 `PasswordAuthentication` 就是这么坏的**。

于是我在注释里写下「用 `99-` 会被静默吃掉」。**然后跑了对照实验**：

| 实验 | `permitrootlogin` |
| --- | --- |
| 我们的文件叫 `00-oracles-root-login.conf` | `yes` ✅ |
| 改名成 `99-oracles-root-login.conf` | **`yes`** ← 打脸 |
| 删掉我们的文件（纯对照） | `prohibit-password` |

**机制没记错，但适用范围记错了**：`PermitRootLogin` **没有任何别人设**，
只有一个设值者时「先到先得」不咬人。换成 `PasswordAuthentication`
（50- 说 yes、60- 说 no，两个设值者）立刻复现：

| 实验 | `passwordauthentication` |
| --- | --- |
| 不加我们的文件 | `yes`（来自 50-） |
| 我们的意图是 `no`，写成 `99-` | **`yes`** ← 被静默忽略 |
| 同样的意图，写成 `00-` | `no` ✅ |

**结论**：`99-` 是「今天能跑通，但依赖『恰好没人跟我抢』这个巧合」。
`00-` 不依赖巧合 —— 哪天 cloud-init 或加固脚本也去写 `PermitRootLogin`，
我们依然是赢的那个。

**方法论**：把「某个关键字上的观察」推广成「所有关键字都这样」，
是**对照实验最容易抓、人眼最难抓**的一类错误 ——
因为推广后的说法**读起来更有价值**，所以更容易被写进注释和文档。

### 52. 同一个功能里的两个 bug 会**互相掩护**

**现场**：救援控制台这个功能，一天里挖出**两个独立 bug**：

| # | bug | 单独存在时的表现 |
| --- | --- | --- |
| A | `_ssh_with_key` 只给**外层** ssh 加 `-i`，`ProxyCommand` 里那跳没有 | `Permission denied (publickey)` |
| B | `open_rescue_console` 建完连接**立刻返回**，此时还是 `CREATING` | 同样 `Permission denied (publickey)` |

两个 bug 的表现**一模一样**。所以：

- 只修 A，用户还是连不上 → 会以为「修错了」
- 只修 B，用户还是连不上 → 同上
- 排查时看到 `Permission denied (publickey)`，会先怀疑**密钥本身**
  （而指纹 `SHA256:y9AS…/Ig` 跟控制台报告的**完全一致**，于是更困惑）

**这也是「🚑 救援」按钮从来没真正跑通过**的完整解释 ——
#37 修掉了 `publicKey` 必填（否则连请求都发不出去），
但 A 和 B 让它在**请求成功之后**依然必然失败。
前一个 bug 被修掉，只是让下一个 bug 从「看不见」变成「看得见」。

**教训**：

1. 一个「从来不工作」的功能，里面往往**不止一个** bug。修掉第一个之后，
   **必须再走一遍完整流程**，别看到代码变了就宣布修好。
2. `Permission denied (publickey)` + 指纹正确，这个组合本身就指向
   「**钥匙没递给对的那一跳**」，而不是钥匙有问题。
3. 端到端真跑一次是唯一能抓住这类 bug 的手段 —— 而且这次能修，
   正是因为**用户给了一台真机器**（`<实例公网IP>`）让我去救。

### 54. 审计/测试的产物本身可能比被审计对象更危险

**现场（两次，同一天）**：

1. 为查「密码有没有落在 /tmp」，我在审计脚本里**写了密码明文**当 grep 模式。
   而 `/tmp` 是 `drwxrwxrwt`、脚本 `644` —— **同机任何用户都能读到**。
   查泄漏的动作本身制造了一个泄漏。
2. 测试里为验证「私钥不会进 spec」，我把 **PEM 私钥头那一行**原样写进了
   测试（`BEGIN … PRIVATE KEY`，前后各五道横杠）—— 项目**自己的密钥
   扫描器立刻报红**（这正是它该做的）。改用**运行时真生成**的私钥后，
   既更忠实（真的是密钥对象）又不在源码里留真形态字面量。

   > 🌀 **这条记录自己又被拦了一次。** 初稿里我为了说清「引用了什么」，
   > 把那行字面量原样抄进了这份文档 —— 扫描器照样报红。
   > 检查工具的**文档**和检查工具的**输入**受同一条规则约束；
   > 写文档时人最容易忘记「这也是源码的一部分」。
   > （本文这一行是**改写后**的：只描述形态，不复制字面量。）

**教训**：

1. 写任何「为了检查 X」的脚本前，先问：**这个脚本自己含不含 X？**
   含的话，它就不是检查工具，是新的泄漏源。
2. 需要比对敏感值时，**别把值写进脚本**。从 600 权限的文件读、
   或从 stdin 读，脚本里只留变量名。
3. 测试夹具需要「真形态」时，优先**运行时生成**而不是写死字面量：
   `generate_ed25519()` 得到的私钥是真的，但源码里干干净净。
   （实在必须写死的，走 `secret-scan:allow` 豁免标记 —— 但那意味着
     你得先能说清「为什么非写死不可」。）

### 55. 用「另抄一份」的常量做端到端测试，等于没测接线

**现场**：为验证「生成的公钥真能走到最终请求体」，我写了一条
穿过 向导状态 → spec → grab 白名单 → `LaunchPlan` → `LaunchInstanceDetails`
的端到端测试。但第一版里，那条白名单是**在测试里另抄的一份**：

```python
allowed = ("ad", "shape", ..., "ssh_public_key")   # ← 从 grab.py 抄来的
plan_kwargs = {k: v for k, v in spec.items() if k in allowed}
```

问题：真正决定「公钥能不能过去」的是 `grab.py` 里那份白名单。
**我抄的这份就算是对的，`grab.py` 那份漏了 `ssh_public_key`，
测试照样绿** —— 因为它根本没经过被测代码。

修法：把白名单抽成 `grab.py` 里的模块级常量 `_PLAN_KWARGS`，
测试直接 `from oracles.services.grab import _PLAN_KWARGS` 用它。
现在改坏 `grab.py` 那份，测试会红。

**教训**：

1. 端到端测试里出现**任何从被测代码抄来的常量**，那条链就断了 ——
   你测的是自己抄的副本，不是代码。
2. 判据：问「如果我把**被测代码**里这个值改坏，这条测试会红吗？」
   答不上来就说明它没接上。
3. 这是 #47「逐段读代码不可能失败」的**变体**：那条讲的是
   「不跑端到端」，这条讲的是「跑了端到端，但绕过被测代码」。

### 56. 校验脚本的**汇总行与退出码**必须由同一个计数器决定

**现场**（2026-09-21，一次部署后的 7 项校验）：

①~⑤ 和 ⑦ 都走 `ok()` / `bad()` 记账。⑥ 是后来临时补的，
图省事直接裸跑一个 `python - <<EOF`、只 `tail` 它的输出。
它抛了异常：

```
AttributeError: module 'oracles.sshkeys' has no attribute '_keys_root'
```

（我猜错了私有函数名。）**而脚本最后照样打印「✅ 部署后校验全部通过」，
退出码 0。**

危害在于 ⑥ 恰好是**最要紧**的那一项 ——「新模块在生产配置下能否加载」。
它挂了说明功能没接上。但因为没进计数器，我差一点把
「有一项挂了」读成「部署完全正常」。

**与 #40 的区别**（这条是新的层）：

| | 失效的是哪一层 |
| --- | --- |
| #40 | **判定层** —— 分不清「干了事」和「什么都没发生」 |
| 本条 | **记账层** —— 判定**给出了否**，但汇总没把它算进去 |

**正确做法**：

1. 每一项检查**必须**走同一个 `ok()` / `bad()` —— 包括临时补的项。
   补一项的成本是「写一个函数」，不是「省掉记账」。
2. 汇总行与 `exit` **只能**读那个计数器；不许有第二处「通过」的写法。
3. 更稳的形态：把每项写成**独立函数**，由一个 runner 统一调用并计数 ——
   这样「忘了记账」在结构上不可能发生，而不是靠自觉。
4. 部署脚本要自证：**故意让它挂一项，看退出码是否非 0**。
   本项目对所有闸门的一贯要求 —— 变异测试证明它会红。

### 57. 假夹具模拟了**你的代码**，却没模拟**平台硬约束**

**现场**（2026-09-21，加「🔑 下载登录密钥」按钮时）：

按钮的 `callback_data` 拼成 `ip:<index>:<token>:key`。**测试全绿** ——
因为 `tests/telegram_harness.py` 的假 `Message` 只把
`reply_text` / `edit_text` 的参数**记下来**，不校验任何东西。

但 Telegram 有一条硬约束：**`callback_data` 最多 64 字节**（UTF-8）。
超了不是「按钮点不动」，而是 `BadRequest: BUTTON_DATA_INVALID` ——
**整条键盘都被拒绝**，用户看到一屏报错、**连菜单都打不开**。

真实数据：`ip:{index}:{token}:` 前缀 9 字节，`token` 正常 6 字符
（`token_urlsafe(4)[:6]`）、**碰撞时退化成 11 字符**（`token_urlsafe(8)`），
最长的 action 是 `terminate`。两者叠加才是真正的最坏情形 ——
**而假夹具里 token 永远是 `"tok"`（3 字符）**。

**同类形态**（都是「本地怎么测都不红、上真环境必炸」）：

| 平台 | 硬约束 | 超了会怎样 |
| --- | --- | --- |
| Telegram `callback_data` | ≤ 64 **字节** | 整条键盘拒绝 |
| Telegram 文本消息 | ≤ 4096 字符 | `Message is too long` |
| Telegram 发文件 | ≤ 50MB（Bot API） | 上传失败 |
| Telegram caption | ≤ 1024 字符 | 拒绝 |

**修法**：

1. 约束写成常量 + **穷举**断言（复用 `test_keyboards.py` 的
   `_all_keyboards()`，新键盘自动纳入）——
   只测「你记得的那个」就是下一个坑。
2. 补一条**最坏输入**用例：11 字符 token + `terminate` + 两位账号号。
3. 上限是**字节**不是字符 → 一律 `len(x.encode("utf-8"))`。
4. 加完做**变异**：注入一个必然越界的字段，证明它会红。

**⚠️ 变异那一环我又踩了一次**（见下一节）：第一版注入的后缀只有 40 字符，
总长 49 字节**仍然合法**，变异体「存活」了。我第一反应是「护栏太弱」，
实际是**变异太弱** —— 差一点去加固一条本来就正确的护栏。

**元教训**：写假夹具时问一句 ——
**「这个假对象替我把哪些东西『变简单』了？」**
它替你省掉的每一条真实校验，都是一个只有上真环境才会炸的盲区。

### 58. 变异体存活时，**先算一遍那个量**，再怀疑护栏

**现场**（2026-09-21，紧接 #57）：

验证「`callback_data` ≤ 64 字节」这条护栏时，我写了两个变异体：
往实例菜单的 callback 里加一段后缀。**两个都存活了。**

第一反应：护栏太弱。但真去算 —— 前缀 `ip:{index}:{token}:` 只有 9 字节，
我加的后缀让总长变成 **49 字节和 46 字节**，**本来就合法**。
护栏判它通过是**正确的**。是我的变异太弱。

```python
# ❌ 弱变异：只自证「文件改了」
assert old in text and text.replace(old, new) != text

# ✅ 强变异：还要自证「改到了能触发断言的程度」
LONG = "x" * 80                  # 固定长度常量，不要手敲长串（会数错）
assert len(LONG.encode("utf-8")) >= 64, "变异太弱：注入的字段不足以越界"
```

**为什么危险**：弱变异存活会给出**反向错误结论** ——
「这条护栏没用」。于是你去加固一条本来就正确的护栏，
或者更糟：**把它删掉**。

**判据（机械、不用判断力）**：
变异之后，**先把「断言要检查的那个量」算出来**，确认它真的跨过了阈值。
别指望「加了个看起来挺长的字符串」就够。

**推广**：这是「变异测试」的第三种自证要求。前两种（目标串**找到了**、
替换位置**唯一**）自证的是「改对了地方」；这一种自证的是
**「改得够狠」**。三件都自证了，`被拦住` 这个结论才有意义。

### 60. 字段在**跨层传递**时被丢掉，于是判定恒走默认分支

**现场**（2026-09-21，查 #59 时顺手撞出来的）：

抢机循环里有一段「不可重试的错误就别再空转了」的逻辑：

```python
NON_RETRYABLE_CODES = frozenset({"NotAuthenticated", "InvalidParameter", ...})

def is_retryable(exc) -> bool:
    code = getattr(exc, "code", None)
    if code:
        return code not in NON_RETRYABLE_CODES
    return True                      # 没有 code → 当作可重试
```

表是对的，函数是对的，循环里也确实调用了它。**但它从来没生效过。**

**证据**（同一段代码，只换异常来源）：

```
NotAuthenticated          exc.code='<不存在>'          is_retryable=True    ← 包装后
NotAuthorizedOrNotFound   exc.code='<不存在>'          is_retryable=True    ← 包装后
InvalidParameter          exc.code='<不存在>'          is_retryable=True    ← 包装后
QuotaExceeded             exc.code='<不存在>'          is_retryable=True    ← 包装后

原始 ServiceError          raw.code='NotAuthenticated'  is_retryable=False   ← 对照
```

**根因**：`oci_gateway` 包装时只传了**翻译后的字符串**：

```python
raise OciApiError(describe_service_error(exc)) from exc      # ❌ code 没了
```

`OciApiError` 只有 message，`getattr(exc, "code", None)` 恒为 `None`
→ 恒为「可重试」→ 那张表是**死代码**。

**为什么特别隐蔽**：这是 #40 的一个新变体。 #40 说的是
「判定分不清『干了事』和『什么都没发生』」；这条是
**判定层完全正常，但它拿到的输入在上一层就被掏空了**。
每一段单独读都对，断点在**层与层之间**。

而且它**不会以故障形式出现** —— 表现为「任务一直转、日志刷屏、
用户等不到结论」，看起来像「网络不好」，不像 bug。

**修法**：

1. `OciApiError` 带上 `code` / `status`（原样保留）。
2. 抽出**唯一**包装入口 `to_api_error(exc)`，4 个包装点全走它 ——
   让「保留字段」这件事只在一个地方发生。
3. **测试必须穿过真实链路**：`test_is_retryable_survives_the_real_wrapping`
   走的是真实的 `AccountClient.call()`，不是自己复制一遍包装逻辑。
   自己复制一遍会**同样丢掉 code**，然后测出「判定是对的」——
   于是这个 bug 永远测不出来（同 #47 / #55）。
4. 补一条「表非空且可达」的断言：否则把整张表清空、
   或让 `is_retryable` 恒返回 `True`，上面那些用例只要期望值全填 `True`
   就照样绿。

**判据（一句话）**：写「根据字段 X 分类」的逻辑时，问 ——
**「这个字段从产生到被读到，中间经过几次重新包装？」**
每一次包装都是一个可能把它丢掉的地方，而 `getattr(..., None)` 的默认值
会让丢掉这件事**静默**。

### 62. 判据里的字段取自**另一个对象** → 条件恒假

`VolumeView.is_attached` 曾经写成：

```python
return bool(self.attached_instance_id) and self.lifecycle_state == "ATTACHED"
```

两个字段名都对、类型都对、比较看着也合理 —— 但 `lifecycle_state` 是
**卷自己**的状态（`list_boot_volumes` 返回的 `BootVolume`），合法值是
`PROVISIONING / RESTORING / AVAILABLE / TERMINATING / TERMINATED / FAULTY`
—— **里面根本没有 `ATTACHED`**（那是 `VolumeAttachment` 的状态，另一个对象）。

于是这个 AND **恒假**：`is_attached` 永远是 `False`。后果不是报错，而是
已挂载的卷在列表里显示「⚪ 未挂载」，菜单照样给出「🗑 删除卷」按钮。

**为什么特别隐蔽**：

- 它**不抛异常、不打日志**。错的是「判据恒假」，而恒假的表现就是
  「这个分支从来没被走到」—— 和「这个分支不需要走」长得一模一样。
- `attached_instance_id` 那一半是**对的**，第一眼看上去「至少挂着时判得对」。
  而 AND 把对的那半也一起废掉了。
- 两个字段**同名同类型**，只是属于不同对象。
  IDE 补全、类型检查、代码审查全都拦不住。

**修法**：

1. 判据只留真正有信息的那一半（`bool(self.attached_instance_id)`），
   并把「为什么不能拿 `lifecycle_state` 比」写进 docstring。
2. 加一条**结构性护栏**：把 SDK 的合法值列表**程序化读出来**，断言
   `"ATTACHED" not in Volume.lifecycle_state 的合法值`。
   这不是在测我们的代码，而是**钉住让 bug 成立的那个前提** ——
   哪天 OCI 真加了 `ATTACHED`，测试会红，提醒你回来重看判定。
3. 假夹具必须**忠实真形态**：状态放在 attachment 对象上，
   而不是给卷对象加一个 `ATTACHED` 状态。夹具要是顺着代码的假设写，
   这个 bug 在测试里永远不会暴露（同 #57）。

**判据（一句话）**：写 `x.字段 == "某个值"` 时，问 ——
**「这个字段的合法取值里，真的有我比的这个值吗？」**
去 SDK 的模型文档里读一眼，成本 10 秒。

### 63. 同一个函数里**两种失败语义并存**

`delete_volume_safe` 是删块卷前的最后一道复核，它有两种失败：

| 失败点 | 原来的行为 |
| --- | --- |
| `availability_domains()` 失败 | `raise` → **一台都不删**（fail-closed ✅） |
| **某个 AD** 的挂载查询失败 | `_safe_call_all` 吞掉异常返回 `[]` → 当成「没挂」→ **照删**（fail-open ❌） |

同一个函数里，两种失败、两种相反的语义。

**为什么特别隐蔽**：**因为已经有一处是 fail-closed 的。**
读代码时看到「列可用域失败 → 抛错不删」，会自然得出
「这个函数对失败很谨慎」的结论 —— 而另一半正好相反。
「已经有一处安全了」比「一处都没有」更危险：它会让你**停止检查**。

而它的失败模式**正好就是这个函数存在的理由**：docstring 写着
「已挂载的直接拒绝 —— 删运行中实例的系统盘是灾难」，
而「挂载查询失败」时它做的恰恰是那件灾难。

**修法**：

1. 把「挂载关系」的获取抽成**一个**函数（`attached_index`），
   返回值里**显式区分**「确实没挂」和「没查成」（`unverified_ads`）。
2. 所有调用方一律 fail-closed：`complete` 为假 → 拒绝给出「可删」的结论。
3. **删掉 `_safe_call_all`** —— 它的语义（吞掉异常返回空列表）
   *就是*这个 bug 本身。

**判据（一句话）**：把这个函数里**每一个 `except`** 列出来，逐个问 ——
**「这里失败，是安全的还是危险的？」** 答案不一致，那就是个洞。

### 64. 两道闸用同一个错误前提 → 「冗余」是假的

删卷这条路上其实有**两道**保护：

1. **UI 层**：已挂载的卷不显示「🗑 删除卷」按钮。
2. **服务层**：`delete_volume_safe` 执行前再实时复核一次挂载关系。

看起来是纵深防御。实际上两道闸**都建立在同一个前提上**：
「挂载状态可以从 `list_*_volume_attachments` 的返回里可靠读出来，
读到什么就是什么」。于是：

- UI 层：查询失败 → 当成没挂 → 卷显示「未挂载」→ **按钮出现**
- 服务层：查询失败 → 当成没挂 → **复核通过** → 删除下发

**两道闸同时失效，而且是因为同一个原因。**
再加一道「也用同一个前提」的闸，只会让人更放心。

**为什么特别隐蔽**：代码审查时，看到「还有服务层复核」就会放过 UI 层，
看到「UI 已经过滤了」就会放过服务层 —— **两边互相背书**。
而它们共享的那个假设，从来没有人单独审过。

**修法**：

1. 把共享的前提**显式化**：抽出 `attached_index`，让「查没查成」成为
   一个**看得见的字段**（`unverified_ads` / `complete`）。
   它一旦有了名字，每一层都会被迫表态。
2. 每一层**各自**对「不确定」表态，而不是假定上一层已经处理了：
   UI 不给入口（`can_delete`），服务层拒绝执行。
3. 补一条**可达性**护栏：断言 `_HANDLERS` 里每个 kind 都有创建点。
   本次顺手扫出 `orphan_delete` **注册了但全仓库没有任何地方创建** ——
   而 `docs/05` 却把它写成了 Bot 的能力（文档陈旧）。

**判据（一句话）**：数「有几道保护」时，先问 ——
**「这几道是基于同一个事实，还是各自独立确认过？」**
基于同一个事实的 N 道闸，就是 1 道。

## 附：容易混淆的两组概念

### 「限额(limit)」 vs 「配额(quota)」

- **limits API** 能查到的叫**限额**（`standard-e2-micro-core-count` 等）
- `bootVolumeQuota` 是**内部 quota 家族名**，limits API 里**查不到**

### 「可用域(AD)」 vs 「故障域(FD)」

- **AD** 是物理隔离的数据中心，免费配额绑在这一级
- **FD** 是 AD 内部的硬件分组，`launch` 时可以不指定（OCI 自动选）

免费账号通常只有 1 个 AD（少数区域有 3 个），
所以 `availability_domains()` 返回 1 或 3 个值是正常的。

## 这些坑是怎么被发现的

绝大部分是在**真实账号池上跑真实操作**踩出来的，不是读文档读出来的。
所以：

- 改这个项目的代码前，先跑 `python scripts/selftest.py` 确认基线是通的
- 加了新功能后，把对应的坑补进这份清单 —— 下一个维护者会感谢你
- `tests/` 里每个「核心断言」都对应上面某一条，别随便删

### 两类坑要用两种手段

| 坑的类型 | 怎么发现 |
| --- | --- |
| **业务坑**（🔴 / 🟠 / 🟡 三节）：配额算错、分页漏数据、删错东西、参数名拼错、常量过时、云厂商默认值不在配置文件里 | 在真实账号池上跑一遍。`selftest.py` 就是干这个的 |
| **元坑**（🧯 那一节）：检查在跑但没在检查；**从没被验证过的接口约定**；**把局部观察推广成通用规律**；字段在跨层传递时被丢掉 | **变异测试** —— 故意破坏被测代码，确认检查真的会失败 |

⚠️ 这两行**刻意只引用章节、不列编号**。原来写的是
「元坑（27–40、47、50、51）」—— 加了新坑没人回来改，于是它从 #52 起
就一直是错的。**任何手写的编号清单都会腐烂**（同 #19）；
改成「看 🧯 那一节」之后它自己不会过期。

第二类**光靠"跑一遍看看"发现不了**，因为它跑起来一切正常。
必须主动去破坏它、看它会不会喊。

第三类（#43、#47 是代表）是**「每段都对、拼起来错」**：

| | 怎么发现 |
| --- | --- |
| 假对象只记录「被调用了」、不校验入参 | 让假对象**校验入参**，或者干脆喂给**真实依赖** |
| 逐段读代码判断「接线正确」 | 这个判断**不可能失败**，所以它没有信息量 |
| 端到端真跑一次 | 唯一能抓住「拼起来错」的手段。贵，但一次就够 |

具体做法：

```bash
# 变异 1：把调用方改回"失败吞成空列表"
perl -pi -e 's/on_error=scan_failed,/on_error=lambda c, exc: [],/' oracles/cli.py
pytest tests/ -q && echo "❌ 漏网！"     # 期望：测试失败

# 变异 2：让 scan_failed 返回 []
perl -pi -e 's/^    return None$/    return []/' oracles/services/__init__.py
pytest tests/ -q && echo "❌ 漏网！"

# 变异 3：渲染层把 None 当空列表
perl -pi -e 's/if v is not None\}/if True\}/' oracles/services/audit.py
pytest tests/ -q && echo "❌ 漏网！"
```

三条都必须被拦住，才算这套测试真的有保护作用。

⚠️ **变异脚本别只靠 `trap` 还原**：进程被 SIGKILL 时 trap 不执行，
改动会留在文件里（本项目踩过 —— 探针数据残留在文档里没被发现，
因为"确认已还原"的那条命令自己也是坏的，见第 30 条）。
要么在独立副本上做，要么事后**独立核实**一遍。
